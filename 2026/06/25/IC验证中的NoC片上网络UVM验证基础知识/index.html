第1章 什么是NoC？（Network-on-Chip）

1.1 从总线到网络：SoC互联架构的演进

在深入了解NoC之前，我们需要先理解"为什么需要NoC"——这涉及SoC互联架构的演进历程。

第一阶段：共享总线（Shared Bus）

早期的SoC使用单一共享总线连接所有模块，如ARM的AMBA AHB、IBM的CoreConnect。

优点：结构简单、面积小、功耗低
缺点：

  • 所有Master共享同一总线，带宽受限
  • 一个Master占用总线时，其他Master必须等待
  • 总线频率受限于最长走线和最多负载
  • 扩展性差，增加Master会降低整体性能

为解决共享总线的瓶颈，业界引入了多层总线（Multi-layer Bus）和交叉开关矩阵（Crossbar）。

  • 超过16个端口时面积急剧增加
  • 长走线影响时序收敛
  • 物理设计（布局布线）困难

NoC的核心思想：

  • 数据以**包（Packet）**的形式传输
  • 包经过多个**路由节点（Router）**从源端"跳转"到目的端
  • 每个路由器只连接到相邻路由器（Mesh拓扑），走线长度短
  • 支持并行传输：多个数据包可以同时在网络中传输

1.2 NoC的精确定义

NoC（Network-on-Chip，片上网络） 是一种在单芯片上实现多模块之间通信的网络化互联架构。它将计算机网络的概念（路由、交换、流量控制、服务质量）引入芯片设计，解决了传统总线架构在带宽、扩展性、物理实现等方面的瓶颈。

NoC的核心特征：

特征 描述
包交换（Packet Switching） 数据被分割成包，每个包独立路由，无需建立端到端的物理连接
多跳传输（Multi-hop） 数据包经过多个路由节点逐跳转发
分布式路由（Distributed Routing） 每个路由器独立做出路由决策，无需中央控制器
并行通信（Parallel Communication） 多个数据流可同时在网络中传输
可扩展性（Scalability） 端口数增加时，面积仅线性增长（O(N)），而非Crossbar的O(N²)

1.4 NoC的关键组成模块

一个完整的NoC由以下核心组件构成：

（1）路由器（Router）

路由器是NoC的核心计算节点，负责接收、存储和转发数据包。一个典型的路由器包含：

子模块 功能 验证重点
输入缓冲区（Input Buffer） 暂存从输入链路到达的包 缓冲区溢出、背压传播
路由逻辑（Route Logic） 计算数据包的目标输出端口 路由表正确性、路由算法
仲裁器（Arbiter） 决定多个输入包共享同一输出端口的顺序 公平性、QoS、优先级反转
交叉开关（Crossbar） 将输入端口连接到输出端口 无阻塞连接、吞吐量
输出缓冲区（Output Buffer） 暂存即将发送到输出链路的包 流控信号、握手时序

（2）网络接口（Network Interface, NI）

NI是IP模块（如CPU、DMA）与NoC路由器之间的适配层。它将IP模块的协议（AXI/AHB/OCP等）转换为NoC内部的包格式，反之亦然。

NI的验证挑战：

  • 协议转换的正确性（AXI事务 ↔ NoC包）
  • 地址到路由端口的映射
  • QoS/优先级在协议之间的映射
  • 背压传播（从NoC到IP协议）

（3）链路（Link）

链路是两个路由器之间（或NI与路由器之间）的物理连接，包含数据线、控制线和流控信号。

1.5 NoC的拓扑结构（Topology）

NoC的拓扑结构定义了路由器之间的连接方式，直接影响系统的延迟、吞吐量、功耗和面积。

1.5.1 常见拓扑结构

拓扑 示意图特征 优点 缺点 典型应用
Mesh（网格） N×M网格，每个节点连接上下左右 结构规整、布线简单、易于扩展 边缘节点延迟高、非均匀 最常用（ARM CMN、自研NoC）
Torus（环形网格） Mesh + 边界节点环形连接 比Mesh延迟更低、更均匀 布线复杂、长环线 高性能计算NoC
Ring（环形） 节点首尾相连成环 面积小、结构简单 带宽受限、单点故障 小规模NoC、缓存一致性网络
Fat Tree（胖树） 多级树状，上层带宽更大 低延迟、高吞吐 布线复杂、面积大 高带宽需求场景（如AI芯片）
Crossbar（交叉开关） 全连接矩阵 最低延迟、最大带宽 O(N²)面积、扩展性差 小规模SoC（<16端口）

1.5.2 Mesh拓扑的验证关注点

Mesh是目前最主流的NoC拓扑，验证时需要特别关注：

坐标系统：每个路由器有(x, y)坐标
路由算法：XY路由（先走X方向，再走Y方向）是最常见的确定性路由
验证点：

  • 从(0,0)到(3,3)的延迟是否与跳数成正比
  • 边角路由器的拥塞是否合理
  • 死锁场景（如四个路由器形成环形依赖）

1.6 NoC的路由机制（Routing）

路由机制决定了一个数据包从源端到达目的端所经过的路径。

1.6.1 路由算法分类

分类 描述 验证重点
确定性路由（Deterministic） 源-目的对的路径固定（如XY路由） 路由表正确性、延迟可预测
自适应路由（Adaptive） 根据网络拥塞动态选择路径 避死锁、实时性、公平性
源路由（Source Routing） 源端指定完整路径，路由器只转发 路径计算正确性、包头格式
表路由（Table-based） 每个路由器查表决定下一跳 路由表配置、动态更新

1.6.2 XY路由（最常用的确定性路由）

  • 每个路由器的输出端口是否正确（东/西/南/北）
  • 包头中的目的地址是否正确解析
  • 是否产生了死锁（XY路由是无死锁的，但验证仍需覆盖）

1.6.3 自适应路由的验证挑战

自适应路由虽然性能更好，但验证复杂度大幅增加：

验证难点：

  1. 路径不确定性：同一个源-目的对的路径随拥塞变化
  2. 死锁验证：自适应路由更容易产生死锁
  3. 活锁验证：包可能永远到达不了目的端
  4. 公平性验证：某些包可能被"饿死"

1.7 NoC的流控机制（Flow Control）

流控机制防止路由器缓冲区溢出，确保数据包不丢失。

1.7.1 常见流控方式

方式 描述 验证要点
Credit-based（信用制） 接收端发送"信用"表示可用缓冲区数量 Credit计数正确、Credit不溢出、无死锁
ACK/NACK（确认/否认） 发送端发送包，接收端回复确认或否认 ACK/NACK时序、重传逻辑
Stop/Go（停-走） 接收端拉高stop信号暂停发送 反压传播延迟、唤醒时序

1.8 NoC的服务质量（QoS）

QoS确保不同类型的流量获得不同的服务等级。

QoS机制 描述 验证重点
优先级仲裁 高优先级包优先获得输出端口 优先级反转、饥饿
带宽分配 为不同流量分配最低带宽保障 带宽测量、公平性
虚通道（VC） 不同流量使用独立的缓冲区通道 VC隔离、死锁避免
流量整形 限制流量的峰值速率 突发处理、令牌桶

1.9 NoC的死锁与活锁

死锁（Deadlock）

死锁是指一组事务循环等待资源，导致永远无法前进。这是NoC验证中最隐蔽、最难复现的问题。

常见的NoC死锁场景：

  • 路由死锁：包在路由环中无限循环
  • 协议死锁：AXI写事务的AW/W/B通道循环依赖
  • 缓冲区死锁：多个方向的数据包填满所有缓冲区

死锁避免策略（验证时需覆盖）：

  • 虚通道（VC）隔离
  • 转向限制（如XY路由禁止某些转向）
  • 逃逸通道（Escape Channel）
  • 路由算法确保无环

活锁（Livelock）

活锁是指包一直在网络中移动但永远到达不了目的端。活锁比死锁更难检测，因为信号"看起来"在活动。

验证策略：

  • 设置"最大跳数"计数器
  • 监控包的"年龄"
  • 统计包到达率的异常

2.2 Arm CoreLink系列NoC产品

Arm是AMBA总线和CoreLink互联IP的领导者，其NoC产品线覆盖从轻量级到高性能的广泛应用。

第3章 NoC验证方法论选择

3.1 什么因素决定验证方法？

在NoC项目中，验证方法的选择取决于以下关键因素：

因素 影响 典型场景
NoC来源 自研 vs 商用IP 自研需要完整验证；商用IP重点是集成验证
是否有真实CPU 是否可将CPU作为激励源 有CPU → 裸机软件驱动；无CPU → UVM虚拟验证
验证目标 功能正确性 vs 性能验证 功能验证用UVM；性能验证需真实流量
时间周期 项目进度约束 需快速收敛 → 用成熟的UVM框架
安全等级 是否需满足ISO 26262 功能安全 → 需要更严格的证据链

3.2 验证方法对比

验证方法 适用场景 优点 缺点
纯UVM虚拟验证 自研NoC、无CPU可用 可控性强、随机性好、调试方便 激励不够"真实"、覆盖可能不充分
CPU裸机软件驱动 商用IP集成、SoC验证 激励真实、验证集成正确性 可控性差、调试复杂
混合验证（UVM + 软件） 复杂SoC、高性能NoC 兼顾真实性和可控性 环境复杂、工具链要求高
