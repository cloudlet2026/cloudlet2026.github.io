一、背景知识：总线与AXI协议基础

1.1 什么是总线？

在芯片设计领域，总线（Bus） 是连接芯片内部各个功能模块（如CPU、内存控制器、外设接口等）的一套公共通信线路和协议规范。它好比城市中的交通网络，数据包就是行驶的车辆，而总线协议就是交通规则。

1.2 AMBA协议族简介

AMBA（Advanced Microcontroller Bus Architecture） 是ARM公司推出的片上总线标准，已成为SoC设计的行业事实标准。AMBA协议族经历了多个版本的演进：

协议版本 代表性总线 主要特点
AMBA 1 APB 简单外设总线
AMBA 2 AHB、APB 高性能、流水线操作
AMBA 3 AXI、AHB-Lite、APB 引入AXI协议
AMBA 4 AXI4、AXI4-Lite、AXI4-Stream 增强型AXI
AMBA 5 CHI、ACE 一致性扩展

1.3 AXI协议的核心特性

AXI（Advanced eXtensible Interface） 是AMBA 3.0及以后版本引入的高性能接口协议。它的设计哲学与现代高性能SoC的需求高度契合，主要体现在以下关键特性：

1.3.1 分离的地址/控制通道与数据通道

AHB总线中，地址和数据共享同一总线相位。而AXI将地址/控制信息与数据分离到独立的通道，实现地址发送和数据传输的解耦。这一设计是支持Outstanding的基础。

        W[写数据通道<br/>WDATA, WVALID, WREADY] --> DUT2
        DUT2 --> B[写响应通道<br/>BRESP, BVALID, BREADY]
    end

1.3.2 独立的读写通道

AXI为读操作和写操作提供独立的通道，这意味着：

  • 读事务和写事务可以完全并发执行
  • 读响应的路径不受写操作的阻塞影响

1.3.3 支持Outstanding事务

Outstanding（待处理传输） 是AXI协议最核心的性能特性之一，下文将详细阐述。

1.3.4 支持乱序响应

AXI协议通过AWID/ARID/WID/RID标识字段，允许从设备以不同于地址发起顺序返回响应，这对提高内存控制器等设备的效率至关重要。

1.4 从AHB到AXI：性能演进视角

为理解Outstanding的价值，有必要对比AHB与AXI的工作方式差异：

特性 AHB AXI
地址与数据相位 共享，分时复用 独立通道，可重叠
Outstanding支持 不支持 支持
响应乱序 不支持 支持（通过ID标识）
读写并发 受限 完全独立
典型带宽利用率 较低 较高

二、Outstanding核心概念详解

2.1 Outstanding的定义

Outstanding（未完成事务数），在AXI协议中指的是：主设备在尚未收到当前事务的最后一个响应（Response）之前，可以额外发起的新事务数量。

更精确地说，一个AXI Master的Outstanding能力定义为：

  • Outstanding Capability = 最大同时处于“已发送地址、未收到最终响应”状态的事务数

2.2 为什么Outstanding很重要？

理解Outstanding的重要性，需要从延迟掩盖（Latency Hiding） 的角度出发。

2.2.1 传统无Outstanding模式（AHB风格）

    sequenceDiagram
    participant M as 主设备
    participant S as 从设备

    M->>S: 发起请求
    Note over M,S: 等待响应
    S-->>M: 响应

    M->>S: 发起请求2
    Note over M,S: 等待响应
    S-->>M: 响应

在这种模式中，总线带宽被浪费在等待从设备响应的时间上。

2.2.2 带Outstanding的高效模式

    sequenceDiagram
    participant M as 主设备
    participant B as 总线
    participant S as 从设备（高延迟）
    
    Note over M,S: 支持Outstanding=3的场景
    M->>B: 发送地址A1
    B->>S: 转发A1
    S-->>S: 处理中(延迟)
    
    M->>B: 发送地址A2（第1笔Outstanding）
    B->>S: 转发A2
    S-->>S: 处理中(延迟)
    
    M->>B: 发送地址A3（第2笔Outstanding）
    B->>S: 转发A3
    S-->>S: 处理中(延迟)
    
    Note over M: 此时还有1笔Outstanding空间
    
    S-->>B: 返回数据D1（响应A1）
    B-->>M: 返回D1
    
    M->>B: 发送地址A4（第3笔Outstanding）
    B->>S: 转发A4

关键洞察：Outstanding允许主设备在等待第一个响应的同时，持续发送后续请求，从而将串行等待时间重叠，有效掩盖了从设备的访问延迟。

2.2.3 性能影响量化

假设：

  • 从设备响应延迟 = 100个时钟周期
  • 总事务数 = 100笔
  • 每个事务的数据传输需1个周期
模式 总耗时 带宽利用率
无Outstanding 100 × (100+1) = 10100周期 约1%
Outstanding=8 100 + (8-1)×100 + 100 = 1100周期 约9%
Outstanding=32 100 + (32-1)×100 + 100 = 3200周期 约3%

注：Outstanding深度并非越大越好，需平衡资源开销和收益。

2.3 Outstanding相关术语辨析

术语 英文 含义

未完成事务 Pending Transaction 已发地址、未收响应的事务
接收能力 Acceptance Capability 接口能接收的Outstanding事务上限
发起能力 Issuing Capability 接口能发起的Outstanding事务上限
Inflight事务 In-flight Transaction 正在总线路径上传输的事务

2.4 Outstanding与ID的关系

AXI协议通过AWID/ARID标识每个事务，支持乱序响应：

  • 同一ID的事务：必须顺序响应
  • 不同ID的事务：可以乱序响应（如果从设备支持）

这一机制与Outstanding紧密配合：

  • 主设备通过分配不同ID，可以追踪多个Outstanding事务
  • 从设备可以按最优顺序处理事务并以不同ID返回

三、NIC-400架构概述

3.1 NIC-400定位与功能

CoreLink NIC-400是ARM提供的高度可配置AXI网络互连IP，主要功能包括：

  • 多主多从互联：支持最多128个Master和64个Slave
  • 协议转换：支持AXI3、AXI4、AHB、APB之间的协议桥接
  • 位宽转换：支持32/64/128位等不同数据位宽转换
  • 时钟域交叉：支持异步时钟域间的数据传输
  • QoS管理：支持基于QoS的仲裁策略

3.3 核心模块详解

3.3.1 ASIB（AXI Slave Interface Block）

ASIB是NIC-400的从设备接口，面向主设备（如CPU）。主要功能：

  • 接收来自Master的AXI事务
  • 解析地址并路由到相应的输出端口
  • 缓冲事务（通过Register Slice或FIFO）
  • 管理Outstanding计数

ASIB的关键配置参数：

参数 说明 典型值
AW_ACCEPT_CAP 写事务接收能力 1-32
AR_ACCEPT_CAP 读事务接收能力 1-127
REGISTER_SLICE_DEPTH 内部缓冲深度 根据需求
CDAS_MODE 死锁避免策略 SS/SSPID/SAS

3.3.2 AMIB（AXI Master Interface Block）

AMIB是NIC-400的主设备接口，面向从设备。主要功能：

  • 向外部Slave发起事务
  • 管理Outstanding发送计数
  • 处理响应返回

AMIB的关键配置参数：

参数 说明 典型值
AW_ISSUE_CAP 写事务发送能力 1-32
AR_ISSUE_CAP 读事务发送能力 1-127

3.3.3 Switch Matrix

Switch Matrix是NIC-400的核心路由引擎，负责：

  • 地址解码与路由选择
  • 多Master到多Slave的仲裁
  • 事务分发与调度
  • CDAS策略执行

3.3.4 Register Slice

Register Slice是NIC-400中用于流水线缓冲的基本单元：

  • Forward Register Slice：添加1级寄存器，增加1笔缓冲能力
  • Full Register Slice：添加2级寄存器，增加2笔缓冲能力
  • 无Register Slice：组合逻辑路径，缓冲能力为0

四、Outstanding能力由谁决定：多级约束系统

NIC-400 的 outstanding 能力不是由主机或从机单方面决定的，而是由互联内部配置、CDAS 以及 ASIB 的缓冲深度共同约束的。主机和从机配置的 outstanding 数只是“期望值”，实际能同时“在路上”的事务数量，受制于以下几个环节。

    flowchart LR
    M[主机<br/>issuing capability] --> A[ASIB<br/>acceptance capability]
    A --> C[CDAS 规则<br/>+ 内部缓冲]
    C --> S[从机<br/>acceptance capability]

    M -.期望值.-> A
    A -.实际接收.-> C
    C -.实际并发.-> S
层级 约束因素 说明
主机侧 主机的 issuing capability 主机自身能发起多少 outstanding 事务
互联入口 ASIB 的 acceptance capability NIC-400 接收主机请求的能力上限
互联内部 CDAS 规则 + 缓冲 决定事务能否真正并行穿过 Switch
从机侧 从机的 acceptance capability 从机自身能接收多少 outstanding 事务

NIC-400 支持的 outstanding 配置范围：

  • 写接受能力：1–32 个事务
  • 读接受能力：1–127 个事务
  • 写发出能力：1–32 个事务
  • 读发出能力：1–127 个事务

关键认知：这些配置参数只约束 NIC-400 内部的事务计数器大小，并不直接创建数据缓冲 FIFO。设置这些值的最简单做法是匹配所连接外部设备的能力。如果你需要额外的缓冲，那是独立的配置选项，不由这些参数控制。

五、CDAS：Outstanding 的核心约束

CDAS（Cyclic Dependency Avoidance Scheme，循环依赖避免方案）是 NIC-400 中最关键、最容易导致 outstanding 行为不符合预期的机制。它本质上是一套防止死锁的事务路由规则。

    subgraph SS["Single Slave (SS) — 最严格"]
        SS1[一个 ASIB 入口的<br/>所有 outstanding 事务<br/>必须指向同一个从机]
    end

    subgraph SSPID["Single Slave per ID (SSPID) — 较灵活"]
        SP1[相同 AWID/ARID 的<br/>outstanding 事务<br/>只能去往同一个从机]
    end

    subgraph SAS["Single Active Slave (SAS) — 写通道"]

    end

5.1 三种 CDAS 模式对比

模式 约束粒度 并发能力 典型场景
SS 整个 ASIB 入口 最弱，只能单目标 简单系统，无并发需求
SSPID 每个 AWID/ARID 较强，不同 ID 可并发 需要并发访问多从机
SAS 写通道活跃目标 中等，防 AW/W 死锁 写通道防死锁

实际影响：如果 CDAS 配置为 SS，主机想同时访问 RAM 和 DDR，即便硬件支持 16 个 outstanding，事务也会被拦住。如果配置为 SSPID，主机用同一个 ID 试图交错访问不同目标，后续事务同样会被阻塞——必须使用不同的 AWID/ARID。

5.2 CDAS策略详解（工程视角）

CDAS策略 工作原理 适用场景 对Outstanding的影响
Single Slave (SS) 同一ASIB上，一次只允许访问一个输出端口。若有Outstanding事务访问Slave A，则访问Slave B的请求被阻塞 单一从设备访问 严重限制并发
Single Slave Per ID (SSPID) 相同AXI ID的事务必须访问同一输出端口；不同ID可访问不同端口 多Slave访问，但Master使用不同ID 有条件并发
Single Active Slave (SAS) 允许访问不同Slave，但若某Slave有未完成的写数据，阻塞其写地址通道 大多数场景 影响较小

    A[选择CDAS策略] --> B{访问模式?}
    B -->|单Slave| C[Single Slave<br/>性能充分]
    B -->|多Slave| D{ID规划?}
    D -->|不同ID对应不同Slave| E[SSPID<br/>推荐]
    D -->|ID复用| F[SAS<br/>最小限制]

    F --> H[需注意写地址阻塞]

6.2 步骤一：系统需求分析

首先明确系统的性能目标：

  • 目标带宽：系统需要达到的数据吞吐量
  • 延迟要求：关键路径的延迟限制
  • 并发模式：Master的访问模式（单Slave vs 多Slave）

6.3.1 主设备Outstanding能力评估

ARM Cortex-R系列CPU 8-16 实时处理器
ARM Cortex-M系列CPU 1-4 微控制器
DMA控制器 取决于设计 数据搬运场景
GPU 32-64 图形处理

从设备能处理的Outstanding事务数受其内部缓冲区限制：

从设备类型 典型Outstanding能力 说明

SRAM控制器 1-8 通常较浅

外设（UART/I2C） 1 无缓冲能力

6.4 步骤三：ASIB接收能力配置

ASIB的接收能力配置需要联立考虑三个因素：

    graph LR
    A[目标Outstanding数] --> D{ASIB接收能力}
    B[Register Slice深度] --> D
    C[Master发起能力] --> D
    D --> E[有效接收能力]

    style E fill:#e1f5fe

配置公式：

  • 配置的ACCEPT_CAP = 目标Outstanding数 - REGISTER_SLICE贡献

其中：

  • 若配置了Full Register Slice，贡献为2
  • 若配置了Forward Register Slice，贡献为1

示例：

  • 目标：支持8笔Outstanding写事务
  • ASIB配置了Full Register Slice（贡献2）
  • 配置值 = 8 - 2 = 6

6.5 步骤四：AMIB发送能力配置

AMIB的发送能力受外部从设备的接收能力限制，应满足：

  • AMIB_ISSUE_CAP ≤ 外部Slave_ACCEPT_CAP

若外部Slave的接收能力为0（表示无限），可合理设置AMIB能力上限。

七、反压机制深入剖析

当主机配置了很大的 outstanding 数，但很快 AWREADY 或 ARREADY 被拉低，说明反压被触发了。反压会沿着链路向上游传导。

7.1 NIC-400 内部反压链路

    flowchart TB
    M["主机 m0_axi4<br/>AWVALID / AWREADY"]
    A["ASIB<br/>地址解码 + 寄存器切片"]
    C["CDAS 约束检查<br/>SS / SSPID / SAS"]
    SW["Switch0 / IB<br/>仲裁器 + 输出队列"]
    S["从机 slave0<br/>内部队列"]

    M -->|"AWVALID"| A
    A --> C
    C -->|"内部请求"| SW
    SW -->|"AWVALID"| S

    S -.->|"AWREADY 低"| SW
    SW -.->|"缓冲满 → AWREADY 低"| C
    C -.->|"CDAS 违反 → 阻塞"| A
    A -.->|"AWREADY 低"| M

反压传导方向：从机 AWREADY 低 → Switch 内部缓冲开始堆积 → Switch 缓冲满后拉低其上游接口的 AWREADY → ASIB 检测到下游无法接收 → ASIB 拉低 m0_axi4 的 AWREADY → 主机停止发送新地址。

7.2 为什么 ASIB 只接受了 3 个事务就反压？

一个典型场景是：主机配置 16 个 outstanding，从机也接收 16 个，但 ASIB 在接受 3 个事务后就拉低 AWREADY。原因是两个约束叠加。

    flowchart LR
    subgraph ASIB["ASIB 内部"]
        B1["寄存器切片<br/>存 2 个事务"]
        B2["当前在途事务<br/>占用 1 个槽位"]
    end

    B1 --> R["实际可接受<br/>2 + 1 = 3"]
    B2 --> R
    R --> F["第 4 个事务到达<br/>→ AWREADY 拉低"]
层级 配置 贡献的 outstanding 容量
ASIB 寄存器切片 存 2 个事务 +2
CDAS (Single Slave) 只允许 1 个目标端口 当前事务占用 1 个“槽位”
实际可接受 2 + 1 = 3 第 4 个被反压

也就是说：ASIB 内部缓冲能存 2 个，第 3 个是“正在传输”的当前事务，第 4 个到达时，CDAS 发现它指向不同端口（或 ID 不符合 SSPID 要求），直接拦住，AWREADY 拉低。

7.3 反压的四种来源

    flowchart TB

    R2["② 从机反压<br/>从机内部队列满<br/>READY 拉低"]

八、Valid-Ready 协议层反压的深层原理

NIC-400 的反压最终落在 AXI 的 AWREADY / ARREADY 信号上。但这里有一个容易被忽略的问题：反压信号需要时间才能传回主机。

8.1 反压信息往返周期（TRRT）

当 AXI 链路上插入了寄存器切片（Register Slice）用于打断组合路径时，反压信号不会“即时”到达主机。

    flowchart LR
    H["主机"] --> S1["slice1"]
    S1 --> S2["slice2"]
    S2 --> S3["slice3"]
    S3 --> SL["从机"]

    SL -.->|"READY 低"| S3
    S3 -.-> S2
    S2 -.-> S1
    S1 -.-> H

    subgraph FWD["forward_stages = 3"]
        S1
        S2
        S3
    end

    subgraph BWD["backward_stages = 3"]
        S3
        S2
        S1
    end
  • TRRT = forward_stages + backward_stages = 6 个周期

含义：从机拉低 READY 后，主机需要 6 个周期才能感知到这个反压。在这 6 个周期内，主机仍然在持续发送新事务。

8.2 Buffer 深度为什么必须 ≥ TRRT？

如果接收端的缓冲深度 B 小于 TRRT，那么反压信号“在途”期间，新到达的事务就会无处存放，导致数据丢失或协议违例。

Arm 的寄存器切片设计为 2-entry skid buffer，正是为了在打破组合路径的同时，维持满吞吐。

    flowchart TB
    C["维持满带宽条件<br/>B_min ≥ BW × TRRT"]
    C --> E1["BW = 每周期 beat 数"]
    C --> E2["TRRT = 反压往返周期"]
    E1 --> R["接收端 buffer 深度 B"]
    E2 --> R

对于每周期 1 beat 的链路（BW=1），TRRT=6 时，接收端 buffer 至少需要 6 个条目才能保证无气泡流水。

8.3 如果 Buffer 不够深，效率会掉多少？

当 B < BW × TRRT 时，每次 FIFO 填满后，反压建立和解除的时间会引入气泡，有效带宽下降：

η=B/(B+TRRT)η = B / (B + TRRT) η=B/(B+TRRT)

    flowchart TB
    subgraph CASE1["Buffer = 3, TRRT = 6"]
        C1["η = 3 / (3 + 6)<br/>= 33.3%"]
    end

    subgraph CASE2["Buffer = 6, TRRT = 6"]
        C2["η = 6 / (6 + 6)<br/>= 50%"]
    end

    subgraph CASE3["Buffer = 12, TRRT = 6"]
        C3["η = 12 / (12 + 6)<br/>= 66.7%"]
    end

如果接收端 FIFO 只有 3 个条目，TRRT=6，链路的有效吞吐只有 1/3。这就是为什么 ASIB 配置了很小的缓冲（如只存 2 个）时，即便主机从机都支持 16 个 outstanding，实际性能也会严重打折。

九、QoS-400：主动调节 Outstanding

QoS-400 是 NIC-400 的可选增强组件，通过主动调控 outstanding 事务的数量来防止某个主机过度占用从机资源。

    flowchart TB
    subgraph QOS["QoS-400 调控机制"]
        RT["事务速率 RT"]
        NT["未完成事务 NT"]
        LT["延迟 LT"]
    end

    RT -->|"RT = NT / LT"| NT
    NT -->|"NT = RT × LT"| LT
    LT -->|"LT = NT / RT"| RT
调控维度 数学关系 作用
事务速率（RT） RT = NT/LT 限制主机发起事务的速率
未完成事务（NT） NT = RT × LT 直接限制 outstanding 数量
延迟（LT） LT = NT/RT 通过 QoS 值动态调整优先级

调控点位置：

    flowchart LR
    M[主机] --> P1["调控点 1<br/>ASIB 入口"]
    P1 --> SW[Switch]
    SW --> P2["调控点 2<br/>内部 IB 节点"]
    P2 --> S[从机]
  • ASIB 入口：在主机进入互联的第一跳进行调控，防止问题流量进入网络
  • 内部 IB 节点：在交换机之间的中间调控点，管理聚合流量

实际意义：当多个主机竞争同一个从机时，QoS-400 的 outstanding 事务调节器可以防止某个主机填满从机的队列，确保其他主机也能获得服务。

十、常见配置陷阱与故障排查

10.1 陷阱一：过度关注能力参数，忽略缓冲深度

现象：将ASIB和AMIB的Outstanding能力均设为较大值，但实际系统无法达到相应并发数。

根因：ASIB内部的Register Slice缓冲深度不足，导致AWREADY/ARREADY提前拉低，产生反压。

    sequenceDiagram
    participant M as Master
    participant ASIB as ASIB<br/>(缓冲深度=2)
    participant S as Slave
    
    M->>ASIB: AW事务1 ✅
    ASIB->>S: 转发事务1
    M->>ASIB: AW事务2 ✅
    ASIB->>S: 转发事务2
    M->>ASIB: AW事务3 ❌ 反压!
    Note over ASIB: 缓冲已满(2笔)
    Note over ASIB: AWREADY=0
    S-->>ASIB: 事务1完成
    ASIB-->>ASIB: 释放1个缓冲
    Note over ASIB: AWREADY=1
    M->>ASIB: AW事务3 ✅ 恢复

解决方案：

  1. 增加Register Slice深度，使其≥目标Outstanding数
  2. 或接受现状，在配置能力参数时考虑缓冲限制

10.2 陷阱二：CDAS策略与访问模式不匹配

现象：配置了较大的Outstanding能力，但实际性能提升不明显。

根因：CDAS配置为"Single Slave"模式，而系统需要交替访问多个Slave。

示例分析：

  • 配置：CDAS = Single Slave
  • 实际访问模式：CPU交替读写DDR和Flash
  • 结果：所有Outstanding事务被串行化，无法并发

解决方案：

  1. 若确实需要多Slave并发访问，改用SSPID或SAS策略
  2. 若使用SSPID，确保不同目标Slave使用不同AXI ID

10.3 陷阱三：主设备和从设备能力不匹配

现象：主设备宣称支持高Outstanding，但实际性能受限。

根因：从设备的接收能力低于主设备发起能力，导致反压。

  • Master发送能力 = 16
  • Slave接收能力 = 4
  • NIC-400 AMIB ISSUE_CAP = 16 ❌ 超配！

解决方案：

  • Master发送能力 = 16
  • Slave接收能力 = 4
  • NIC-400 AMIB ISSUE_CAP = min(16, 4) = 4 ✅

10.4 陷阱四：忽视AXI ID的分配与管理

现象：配置了SSPID策略，但Outstanding效果仍不理想。

根因：多个目标Slave使用了相同的AXI ID，导致SSPID策略将其视为同一ID，强制串行化。

解决方案：

  • 建立ID分配规范，不同目标Slave使用不同ID
  • 或在Master端实现ID动态分配逻辑

10.5 故障排查流程

    flowchart TD
    A[性能未达预期] --> B{检查ASIB<br/>缓冲深度}
    B -->|不足| C[增加Register Slice深度]

11.3 一个真实的调试场景

根据 Arm 社区的实际案例：主机配置 outstanding=16，从机接收=16，但 ASIB 在第 3 个事务后拉低 AWREADY。用上述代码逻辑解释：

    sequenceDiagram
    participant M as 主机
    participant A as ASIB
    participant S as 从机

    M->>A: 第 1 个事务
    A->>S: 接受，outstanding_cnt = 1
    M->>A: 第 2 个事务
    A->>S: 接受，outstanding_cnt = 2
    M->>A: 第 3 个事务
    A->>S: 接受，outstanding_cnt = 3
    M->>A: 第 4 个事务
    Note over A: outstanding_cnt >= 3<br/>fifo_full = 1
    A-->>M: AWREADY = 0 (反压)
  • ASIB_BUFFER_DEPTH = 2（寄存器切片存 2 个）
  • effective_max = 3
  • 第 1、2 个事务存入缓冲，第 3 个事务被下游接受（outstanding_cnt = 3）
  • 第 4 个事务到达时，outstanding_cnt >= 3 → fifo_full = 1 → awready = 0

如果同时有 CDAS 约束（SS 且目标端口交替），则第 4 个事务还会被 cdas_blocked 拦住，反压更早出现。

十三、总结与最佳实践

13.1 核心要点回顾

本文围绕NIC-400的Outstanding配置与验证，从概念到实践系统阐述了：

  1. 概念层面：Outstanding是AXI协议的核心性能特性，通过地址通道与数据通道的分离实现延迟掩盖
  2. 架构层面：NIC-400通过ASIB、AMIB、Switch Matrix和Register Slice等模块协同实现Outstanding管理
  3. 配置层面：需要综合考虑接收能力、发送能力、缓冲深度和CDAS策略四个维度
  4. 反压层面：反压是 CDAS 规则 × ASIB 缓冲深度 × 协议层 TRRT 三者共同作用的结果，调大主机/从机的 outstanding 配置参数并不能绕过这些约束
  5. 验证层面：基于UVM和AXI VIP，通过定向测试、随机测试和覆盖率监控确保配置正确生效

13.3 最佳实践建议

  1. 自上而下规划：从系统性能需求出发，逐层确定Outstanding配置
  2. 缓冲优先于能力：确保物理缓冲足够，再配置能力参数
  3. CDAS策略先行：根据访问模式尽早确定CDAS策略，避免后期修改
  4. 验证左移：在配置阶段就建立验证计划，并行推进
  5. ID规划规范化：建立全芯片的AXI ID分配规范，避免冲突
  6. 性能实测：在FPGA或仿真中实测实际吞吐量，验证配置效果
  7. 文档化：将配置决策和理由文档化，便于后续维护
