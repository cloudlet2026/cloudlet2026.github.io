玄铁 C910/C920 Cache 与写合并详解

发表于2026-09-11|更新于2026-09-12
|浏览量:

第一章 为什么需要 Cache

CPU 核心跑得非常快，C910 主频可达 2GHz 以上，一个时钟周期约 0.5 纳秒。但 DDR 内存响应慢得多，访问一次可能需要几十甚至上百纳秒。如果 CPU 每次要数据都直接去 DDR 拿，流水线会大量时间空转。

Cache（缓存）就是放在 CPU 旁边的小书架，把最常用的数据先搬过来。CPU 先从 Cache 找，找到直接用；找不到再去 DDR 拿，同时把周围数据一起搬回来备用。

C910/C920 采用两级缓存：

  • L1 Cache：最小最快，紧挨核心，分为 I-Cache（放指令）和 D-Cache（放数据）
  • L2 Cache：大一些慢一些，同一 Cluster 内多个核心共享

第二章 Cache 的基本单位：缓存行

Cache 不是按字节从 DDR 拿数据，而是按块搬。这个块叫缓存行（Cache Line）。C910/C920 的缓存行大小是 64 字节。

为什么按块搬？因为程序访问数据有空间局部性：用了数组第 0 个元素，大概率马上会用第 1、2、3 个。一次拿 64 字节，后面几十次访问可能都命中。

64 字节这个数字是全文最关键的常数，所有写合并行为都围绕它展开。

第三章 组与路：储物柜比喻

3.1 Cache 的二维结构

C910 的 L1 D-Cache 是 64KB，2 路组相联，64 字节缓存行。这三个数字决定了一个二维表格：

计算：512 组 × 2 路 × 64 字节 = 64KB，刚好对上。

把它想象成一排储物柜：一共 512 个柜子（组），每个柜子有 上下两层（2 路），每层只能放一个 64 字节的箱子（缓存行）。

3.2 地址如何映射

物理地址被拆成三段：

Tag 索引 9位 偏移 6位
  • 偏移：6 位，决定访问缓存行内第几个字节
  • 索引：9 位，决定去哪个组（0~511）
  • 标签：剩余高位，确认"这个组里的这一路，是不是我要的地址"

硬件流程：用索引定位组 → 同时读出两路 Tag → 与地址 Tag 比较 → 匹配则命中，都不匹配则缺失。

3.3 "2 路"到底解决什么

如果每组只有 1 路（直接映射），两个索引相同的不同地址会互相驱逐，反复缺失。2 路相当于每个组准备两个停车位，两个索引相同的地址各停一个。

“2 路"不是"同时处理两个访问”，而是"同一个组里有两个候选位置"。 硬件每次只处理一个访问，同时看两个位置判断命中哪个。

C910 的 L1 I-Cache 采用 VIPT（虚拟索引物理标签），D-Cache 采用 PIPT（物理索引物理标签）。VIPT 让索引查找与 TLB 翻译并行，加速取指；PIPT 需先翻译再索引，但避免了虚拟地址别名问题。L2 为 16 路组相联，两个 bank，由物理地址第 6 位选择。

3.4 连续写多个缓存行时，箱子怎么放

"路"是储物柜的层数，"缓存行"是要放的箱子。

当写入 80 字节时，数据跨越两个缓存行，也就是两个箱子。这两个箱子各自找自己的柜子（组）：

  • 箱 1 的地址在 [0x1000, 0x103F]，索引位指向某个组（比如组 5）
  • 箱 2 的地址在 [0x1040, 0x107F]，地址比箱 1 大 64 字节，索引位通常连续，指向下一个组（组 6）

所以两个箱子大概率去两个相邻的柜子，每个柜子各占一层。

不是"两个箱子塞进同一个柜子的上下两层"。

上下两层（两路）是给两个碰巧映射到同一个柜子的不同地址准备的，不是给一次连续写入准备的。比如地址 A 和地址 B 相差 32KB（恰好是组索引的整数倍），它们会映射到同一个组，这时才需要用到两路，各占一层。

第四章 三类访存空间

不是所有地址都能进 Cache。玄铁用页表项（PTE）里的 5 个比特标记地址区域属性：

类型 编码 进 Cache 写合并 顺序 用在哪
可缓存 PMA 01110 ✅ ✅ 弱序 普通 DDR 内存
可高缓存 NC 00110 ❌ ✅ 弱序 写多读少外设
不可缓存 IO 10010 ❌ ❌ 强序 UART/PLIC
  • 可缓存空间（PMA）：正常 DDR 内存，读写走 Cache，写可合并
  • 可高缓存空间（NC）：数据不进 Cache，但写可进写缓冲合并，适合批量配置外设寄存器
  • 不可缓存空间（IO）：每次写立即到达设备，不合并、不乱序，UART 发送寄存器必须如此

只有 PMA 和 NC 支持写合并，IO 空间永远一次写对应一次总线事务。

硬件硬编码行为： NC 和 IO 的 SH（Shareable）属性被硬件固定为 1，软件无法配置。即使单核访问这些区域，硬件也按 Shareable 语义处理，确保与 DMA 设备的一致性。

    IO --> DIRECT["直达设备<br/>不可乱序"]

第五章 写合并的原理

5.1 为什么需要写合并

CPU 执行一条 store 指令，比如 sw a0, 0(sp)，只是把 4 个字节写进内存。如果每条 store 都立刻变成一次独立的总线事务发往 DDR，会发生什么？

C910 的 AXI 主接口位宽是 128 bit（16 字节）。一条 4 字节的 store 如果单独发一次总线事务，有效载荷只有 4 字节，带宽利用率 25%。每次事务还要经历仲裁、地址握手、数据握手，开销远大于 4 字节数据本身。

程序里的 store 往往是连续的。一个 memset 循环，或者结构体初始化，会产生大量地址相邻的写。如果每条都单独发，总线上会挤满"只带 4 字节"的小事务。

硬件的自然选择：把多个写先攒起来，够大了再一起发。 这就是存储合并缓冲（Store Merge Buffer / Write Memory Buffer，WMB）的出发点。

第一个原理性结论：写合并的目的是让总线事务的有效载荷尽量大，减少事务数量。

5.2 攒到多大才能发

硬件不能无限攒下去，必须有一个"该发了"的判定条件。这个条件有两个维度：

维度 触发条件 本质原因
缓冲容量 物理容量满了 硬件资源有限
地址连续性 下一个写与已攒数据不再连续 一次 AXI 突发要求地址连续

写合并边界不是固定常数，而是“等于缓存行大小”的变量。

    flowchart TD
    STORE["store 指令到达 WMB"] --> CHECK1{"缓冲满了吗?"}
    CHECK1 -->|"满了"| EMIT1["发出已攒数据"]
    CHECK1 -->|"没满"| CHECK2{"下一个写地址<br/>与已攒数据连续吗?"}
    CHECK2 -->|"连续"| ACCUM["继续攒"]
    CHECK2 -->|"不连续"| EMIT2["切断,发出已攒数据"]
    EMIT2 --> RESTART["从新地址重新攒"]
    ACCUM --> CHECK1
    EMIT1 --> AXI["AXI 总线"]
    RESTART --> CHECK1

5.3 缓存行为什么成为合并的硬边界

缓存行是 Cache 的原子操作单位。 C910 的 L1 D-Cache 是 64KB、2 路组相联、64 字节缓存行。Cache 的 tag array 和 dirty array 都以 64 字节为单位管理：

  • 一个 tag 对应一整条 64 字节缓存行
  • 一个 dirty 位标记一整条缓存行的脏/干净状态
  • 一次替换搬走一整条 64 字节

Cache 里不存在"半个缓存行"的概念。 一条缓存行要么整个在，要么整个不在；要么整个脏，要么整个干净。

假设 WMB 攒了一个 80 字节的写，地址范围 [0x1000, 0x104F]，跨越了 [0x1000, 0x103F] 和 [0x1040, 0x107F] 两条缓存行。这个写请求交给 Cache 时，硬件面临尴尬局面：

  • 前 64 字节要更新缓存行 A 的 tag 和 dirty 位
  • 后 16 字节要更新缓存行 B 的 tag 和 dirty 位

一次操作要同时触及两条缓存行的标签和状态。 而 Cache 的 tag array 每次只能对一个索引做一次比较和更新。如果还伴随写分配（Write Allocate），硬件要先读入缓存行 A 和 B，分别合并，再分别标记脏——这已经变成两次独立的 Cache 操作。

硬件的选择：干脆不让合并跨越缓存行边界。 在边界处强行切断，把已攒数据作为一次事务发出，从新缓存行起始处重新开始攒。

第二个原理性结论：Cache 以 64 字节为原子单位管理，合并也必须以 64 字节为界，否则后续 Cache 更新无法用统一原子操作完成。

切断发生在缓存行的边界，即地址 (A & ~0x3F) + 0x40 处，A 是当前缓存行的起始地址。如果从 0x1010 开始连续写，缓存行边界在 0x1040。写入 [0x1010, 0x103F] 时都在同一行内，可以合并；写到 0x1040 时跨入新行，合并切断。

“每次跨过一条缓存行的终点就切断”。

    flowchart TD
    STORE["CPU store 指令"] --> ATTR{"地址属性"}
    ATTR -->|"IO"| NOMERGE["不合并<br/>单个事务"]
    ATTR -->|"PMA/NC"| SMB["进入存储合并缓冲"]
    SMB --> CHECK{"跨越 64B 边界?"}
    CHECK -->|"未跨越"| ACCUM["继续积累合并"]
    CHECK -->|"跨越"| FLUSH["切断合并<br/>发出已积累数据"]
    FLUSH --> RESTART["从新缓存行重新积累"]
    ACCUM --> FULL{"缓冲已满?"}
    FULL -->|"未满"| WAIT["等待更多写"]
    FULL -->|"已满"| EMIT["发出合并突发"]
    RESTART --> ACCUM
    WAIT --> CHECK
    EMIT --> AXI["AXI 总线"]
    NOMERGE --> AXI

第六章 举例说明：三种写入模式

例一：连续写 16 字节（从 0x1000 开始）

写入地址序列：0x1000, 0x1004, 0x1008, 0x100C，共 4 次 4 字节写，总范围 [0x1000, 0x100F]。

缓存行归属分析：

  • 0x1000 落在缓存行 [0x1000, 0x103F]
  • 0x1004 落在缓存行 [0x1000, 0x103F]
  • 0x1008 落在缓存行 [0x1000, 0x103F]
  • 0x100C 落在缓存行 [0x1000, 0x103F]

四次写入全部落在同一条缓存行内。WMB 检测到地址连续，持续攒下去。攒够 16 字节后发出一个突发。

结果：1 个突发（len=0, size=4，即 1 拍 × 16 字节 = 16 字节）。

例二：连续写 80 字节（从 0x1000 开始）

写入范围 [0x1000, 0x104F]，共 80 字节。

缓存行归属分析：

部分 地址范围 所属缓存行 覆盖情况
前 64 字节 [0x1000, 0x103F] 行 1 [0x1000, 0x103F] 完整覆盖
后 16 字节 [0x1040, 0x104F] 行 2 [0x1040, 0x107F] 仅前 16 字节

WMB 在写到 0x1040 时检测到跨越了行 1 的边界，切断合并，把行 1 的 64 字节发出；然后从 0x1040 重新攒行 2 的 16 字节，写完发出。

结果：2 个事务，类型不同。

  • 行 1 完整 64 字节 → WriteLineUnique（写满整行）
  • 行 2 仅 16 字节 → WriteUnique（部分写）

例三：每隔 64 字节写（从 0x1000 开始）

写入地址序列：0x1000, 0x1040, 0x1080，每次写 4 字节。

缓存行归属分析：

写入地址 所属缓存行 与前一次的关系
0x1000 行 1 [0x1000, 0x103F] —
0x1040 行 2 [0x1040, 0x107F] 跨越了行 1 的终点
0x1080 行 3 [0x1080, 0x10BF] 跨越了行 2 的终点

每次写入都落在新缓存行的起始处。WMB 在 0x1040 到来时切断合并，把 0x1000 那次写先发出；从 0x1040 重新攒，但 0x1080 又立刻跨边界，再次切断。

结果：3 个独立事务。

  • 0x1000 → WriteUnique（仅 4 字节）
  • 0x1040 → WriteUnique（仅 4 字节）
  • 0x1080 → WriteUnique（仅 4 字节）

从例子中提炼规律

写入模式 缓存行归属 合并行为 事务数量 事务类型
连续写 16B 同一行 持续合并 1 取决于是否写满整行
连续写 80B 跨两行 行边界切断 2 WriteLineUnique + WriteUnique
隔 64B 写 每次新行 每次切断 每次写入 1 个 全部 WriteUnique

规律：合并能否发生，取决于写入地址是否落在同一条缓存行内。跨行必切断，这是缓存行作为 Cache 原子操作单位的必然结果。

第七章 事务类型为什么重要

从例二和例三可以看到，事务类型不只是"数量多少"的问题，还影响其他核的一致性处理代价。

WMB 发出事务时，根据"是否写满整条缓存行"选择不同事务类型：

条件 事务类型 其他核 CIU 的处理
写满整条缓存行 WriteLineUnique MakeInvalid：直接删除副本，无需回写
只写了部分 WriteUnique CleanInvalid：先写回脏数据，再删除副本

关键差异：

  • WriteLineUnique：写方提供了完整一行新数据，旧数据无保留价值，其他核直接删掉
  • WriteUnique：只写了部分，其他核需要先把脏缓存行写回，再删除副本。ARM 文档明确指出，WriteUniquePtl 总是触发 read-modify-write 序列

第三个原理性结论：连续写不仅事务数量少，还因为写满整行而让其他核免去"先写回脏数据"的开销。隔步长写则每次触发 CleanInvalid 和 read-modify-write，一致性带宽被严重消耗。

在 8 核 C920 系统中，如果多个核频繁写共享数据，部分写会触发大量 CleanInvalid，性能差距会非常明显。

第八章 完整数据流

从 CPU 执行 store 到数据落到 DDR，完整路径是：

store 指令 → LSU 流水线 → WMB 合并 → 判定是否跨缓存行 → 选择事务类型 → ACE 总线 → CIU 监听处理 → L2/DDR

    graph TB
    A["CPU store 指令"] --> B["地址翻译<br/>虚拟→物理"]
    B --> C{"PTE 属性"}
    C -->|"PMA"| D["查 L1 D-Cache"]
    C -->|"NC"| G["存储合并缓冲"]
    C -->|"IO"| H["直接发往设备"]
    D -->|"命中"| E["写入 Cache"]
    D -->|"缺失"| F["写分配或写穿透"]
    E --> I["脏数据等待写回"]
    F --> G
    I --> G
    G --> J{"跨 64B 边界?"}
    J -->|"未跨"| K["继续积累"]
    J -->|"跨越"| L["切断并发突发"]
    K --> M["AXI 总线"]
    L --> M
    M --> N["DDR 控制器"]

两个核心决策点：

  1. 是否跨缓存行 → 决定合并能否继续
  2. 是否写满整行 → 决定发出的事务类型

第九章 软件层面的 Cache 操作

9.1 CMO 指令

RISC-V 标准 Zicbom 定义：cbo.clean（写回保留）、cbo.inval（无效不写回）、cbo.flush（写回并无效）。CMO 指令忽略缓存属性，对不可缓存地址执行也不报错，但可能无实际效果。

9.2 必须干预的场景

  • DMA 前：Clean D-Cache 确保数据落主存
  • DMA 后：Invalidate D-Cache 避免读到旧值
  • 自修改代码：Invalidate I-Cache
