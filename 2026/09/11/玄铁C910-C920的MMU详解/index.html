玄铁C910/C920的MMU详解

发表于2026-09-11|更新于2026-09-12
|浏览量:

引言

C910 和 C920 是阿里平头哥玄铁系列的两款 64 位 RISC-V 处理器，均采用 12 级乱序流水线，支持 RV64GC 及多核簇扩展。C920 相比 C910 的最大差异是从 RVV 0.7.1 升级到 RVV 1.0，并可选配 128/256 位向量单元。

两者共享同一套内存子系统架构：MMU 采用 SV39 标准 + 两级 TLB 结构，Cache 采用“私有 L1 + 共享 L2”的层次化设计。理解这套架构，是进行 IC 验证的基础。

关键设计事实：

  • L1 Cache 和 TLB 是每核私有的，L2 是簇内共享的。
  • CIU 处于 L1 和 L2 之间，是所有一致性流量（Cache Snoop + TLB Shootdown）的枢纽。
  • C920 的向量扩展对 DTLB 和 L1 D-Cache 的带宽提出了更高要求。

二、MMU：虚拟地址到物理地址的翻译引擎

MMU（Memory Management Unit，内存管理单元）是一种硬件模块，用于在CPU和内存之间实现虚拟内存管理。

2.1 为什么需要 MMU

没有 MMU 时，程序直接面对物理内存，存在两个致命问题：

  • 隔离性差：程序 A 可以随意读写程序 B 的内存。
  • 地址空间不够用：每个程序独占连续物理内存，碎片化严重。

MMU 通过分页机制解决：虚拟地址空间切成 4KB 的“页”，物理内存切成同样大小的“页框”，页表记录“哪一页对应哪一页框”。

2.2 页表遍历的代价

SV39 标准下，虚拟地址被切成 4 个部分：VPN[2]、VPN[1]、VPN[0]、页内偏移。页表是三级树状结构，一次完整的 TLB 缺失，PTW 需要最多四次内存访问。

假设内存访问延迟 100 个周期，一次翻译就要多花 300 个周期。如果每次访存都这样，CPU 性能会直接崩掉。这就是 TLB 存在的意义。

2.3 TLB 的两级结构

C910 的 TLB 组织是 “第一级全相联小容量 + 第二级组相联大容量”。

第一级 UTLB（DTLB/ITLB）：

特性 DTLB ITLB
结构 全相联 全相联
表项数 17 与 DTLB 类似
端口 双读端口（支持 Load/Store 双发射并行转换） 单端口
大页处理 前 16 项存 4KB/2MB，第 17 项存 1GB 类似

  • 但 DTLB/ITLB 不存 ASID，写 SATP 寄存器（切换页表根）时必须全部刷新 UTLB。

2.4 PTW 页表遍历流程

PTW 是 TLB 缺失后真正去读页表的模块。

    START["SATP.ppn<br/>根页表物理基址"] --> L1["第1次访存<br/>根页表基址 + VPN[2]×8<br/>读根页表项"]

    CHK2 -->|是| DONE2MB["完成<br/>得到 2MB 大页"]
    CHK2 -->|否| L3["第3次访存<br/>上级PPN + VPN[0]×8<br/>读叶子页表项"]
    L3 --> CHK3{"叶表项?"}

    DONE --> PERM{"权限检查<br/>X/W/R"}
    DONE2MB --> PERM
    DONE4KB --> PERM
    PERM -->|通过| OK["TLB 回填"]
    PERM -->|违反| FAULT

PTW 与 DCache 的借用关系：PTW 读页表时不是独立访问内存，而是**“借用” LSU 的 DC 流水级**。PTW 向 MCIC 发送请求，若 DCache 响应，则读操作插入 LSU 的 DC 流水线。在 PTW 完成之前，LSU 的 DC 流水级会停顿来处理这个“借道”访问。这就是为什么 TLB 缺失虽然不阻塞流水线前端，但会占用 LSU 的访存带宽。

2.5 DTLB 缺失的“冻结-唤醒”机制

这是 C910 区别于顺序核的关键设计。

    flowchart TB
    LSIQ["LSU 乱序队列 LSIQ"] --> INA["指令 A<br/>虚拟地址 VA_A"]
    LSIQ --> INB["指令 B<br/>继续乱序发射"]

    INA --> AG["AG 级地址生成"]
    AG --> DTLBQ["DTLB 查询"]
    DTLBQ --> MISS{"命中?"}
    MISS -->|命中| PA["得到物理地址<br/>继续执行"]
    MISS -->|缺失| FREEZE["冻结 LSIQ 对应项<br/>记录 VA_A<br/>分配 Refill ID"]
    FREEZE --> PTWGO["PTW 开始页表遍历"]
    PTWGO --> FILL["回填完成<br/>写入 DTLB"]
    FILL --> WAKE["唤醒 LSIQ 表项<br/>重新发射指令 A"]
    WAKE --> AG

    INB --> AG2["AG 级<br/>不受 A 缺失影响"]
    AG2 --> DTLBQ2["DTLB 查询"]
    DTLBQ2 --> PA2["得到物理地址"]

两个缺失的仲裁：如果 Load 和 Store 同时发生 DTLB 缺失，DTLB 比较指令 ID，优先处理更旧的指令。这是乱序处理器中“以程序顺序处理异常”原则的体现——异常（TLB 缺失最终可能变成 Page Fault）必须按程序顺序报告。

三、Cache：让数据离 CPU 更近

MMU 解决了“地址翻译”，但物理内存本身仍然很慢。Cache 的任务是把最近用过的数据放在离 CPU 更近的小容量存储器里。

3.1 Cache 层次

层级 容量 位置 协议 索引方式
L1 I-Cache 32/64KB 每核私有 — VIPT
L1 D-Cache 32/64KB 每核私有 MESI PIPT
L2 Cache 256KB~8MB 簇内共享 MOESI —

L1 是哈佛结构（指令和数据分开），L2 统一缓存所有数据和指令。

8 Bank 结构的意义：Data Array 分 8 个 bank，每个 bank 一次读 128bit。L1 D-Cache 一个周期最多可以并行服务两个 128bit 的访问（对应双发射 LSU）。当 LSU 双流水线同时访问 D-Cache 时，只要落在不同 bank，就能并发处理。

自适应写分配：常规 Cache 在写缺失时会把整个 Cache 行从内存读进来（Write-Allocate）。C910 检测到程序在连续地址上写入时（如 memset），切换为 Write-No-Allocate——直接写穿到下一级，不占用 L1 Cache 行。这避免了“写了就要驱逐”的无效占用。

为什么 I-Cache 用 VIPT，D-Cache 用 PIPT：

  • VIPT 允许用虚拟地址低位索引 Cache 的同时，MMU 并行进行地址翻译，降低取指延迟。但容量超过 4KB×路数时有别名风险。
  • PIPT 从根本上消除了别名问题，同一个物理地址永远映射到同一个 Cache Set，软件不需要处理 Cache 别名。数据访问路径对延迟不如取指那么敏感，所以用 PIPT。

3.3 MESI/MOESI 状态转换

    stateDiagram-v2
    [*] --> I
    I --> E: 本地读缺失<br/>其他核无副本
    I --> S: 本地读缺失<br/>其他核有副本
    I --> M: 本地写缺失
    E --> M: 本地写命中
    E --> S: 其他核读<br/>Snoop 响应
    E --> I: 其他核写<br/>Snoop 响应
    M --> S: 其他核读<br/>写回并转共享
    M --> I: 其他核写<br/>写回并失效
    M --> O: 其他核读<br/>转为 Owned
    S --> M: 本地写命中<br/>其他核副本失效
    S --> I: 其他核写<br/>Snoop 失效
    O --> S: 其他核读<br/>继续共享
    O --> I: 其他核写<br/>写回并失效
    O --> M: 本地写命中
协议 使用位置 状态数 核心差异
MESI L1 D-Cache 4 没有 Owned，脏数据必须写回内存
MOESI L2 Cache 5 多了 O（Owned）：脏数据但可被其他核共享

O 状态的实际意义：核 A 的 L1 有一个 Modified 行，核 B 要读。MESI 下核 A 必须先写回内存，核 B 再从 L2 读。MOESI 下核 A 的行转为 O，核 B 直接从核 A 的 Cache 通过 CIU 取数据（Cache-to-Cache Transfer），不需要经过内存，显著降低多核共享数据延迟。

3.4 多核假共享

假设核 0 和核 1 分别频繁写两个不同的变量，但这两个变量恰好落在同一个 64 字节 Cache 行里：

  1. 核 0 写变量 A → 拿到 Cache 行的 M 状态，核 1 的副本被 Invalid。
  2. 核 1 写变量 B → 核 0 的行被 Invalid，核 1 拿到 M。
  3. 核 0 再写变量 A → 核 1 又被 Invalid……

结果是：两个核在逻辑上访问的是不同数据，物理上却在反复争夺同一行 Cache，性能急剧下降。这就是假共享（False Sharing）。C910 的 L2 MOESI 和 CIU 硬件一致性机制，保证这种场景下数据依然正确（性能损失由软件通过 padding 等方式规避）。

四、CIU：Cache 一致性与 TLB 一致性的统一枢纽

CIU（Coherence Interface Unit）同时处理 Cache 一致性和 TLB 一致性的流量。

    subgraph Cores["多核"]
        direction TB
        C0["Core 0<br/>L1 + MMU"]
        C1["Core 1<br/>L1 + MMU"]
        CN["Core N<br/>L1 + MMU"]
    end

    subgraph CIUDetail["CIU 内部"]
        direction TB
        REQQ["一致性请求队列 + 仲裁"]
        SNOOP["Snoop Filter<br/>向各核广播<br/>Cache 失效请求"]
        SFENCE["sfence 广播队列<br/>向各核广播<br/>TLB Shootdown"]
    end

    L2["L2 Cache"]
    MEM["内存控制器"]

    C0 <-->|"Snoop Req / Rsp<br/>sfence.vma"| CIUDetail
    C1 <-->|"Snoop Req / Rsp<br/>sfence.vma"| CIUDetail
    CN <-->|"Snoop Req / Rsp<br/>sfence.vma"| CIUDetail

    REQQ --> SNOOP
    REQQ --> SFENCE
    CIUDetail --> L2
    L2 --> MEM

关键理解：核 0 执行 sfence.vma 后，刷新请求不是点对点发给其他核，而是先发给 CIU，由 CIU 广播到所有核。每个核内部有一个队列缓冲来自 CIU 的刷新请求，并进行仲裁（可能同时有 Cache Snoop 和 TLB 刷新请求到达）。这种“集中广播”设计保证了所有核看到的一致性事件顺序一致。

sfence.vma rs1, rs2 的语义：

  • rs1=x0, rs2=x0：刷新所有 TLB 表项。
  • rs1!=x0：只刷新虚拟页号匹配的表项。
  • rs2!=x0：只刷新 ASID 匹配的表项。

五、融合理解：多核进程迁移的完整数据流

把 MMU 和 Cache 放在一起，走一遍多核进程迁移的完整数据流。场景：进程 P 原本跑在核 0，现在 OS 决定把它迁移到核 1。

    sequenceDiagram
    participant OS as OS / 核0
    participant CIU as CIU
    participant C0 as Core 0<br/>L1 + TLB
    participant C1 as Core 1<br/>L1 + TLB
    participant L2 as L2 Cache

    Note over OS,C1: 进程 P 从核0迁移到核1

    OS->>OS: 修改进程 P 的页表项
    OS->>C0: 执行 sfence.vma rs1, rs2
    C0->>CIU: 发送 TLB 刷新请求
    CIU->>C0: 广播刷新（本地也刷）
    CIU->>C1: 广播刷新（VPN=rs1, ASID=rs2）
    C1->>C1: 无效化 JTLB 对应表项<br/>逐出 DTLB/ITLB 表项

    Note over C1: 核1开始执行进程 P

    C1->>C1: ITLB 缺失 → PTW 读页表
    C1->>C1: DTLB 缺失 → PTW 读页表
    C1->>L2: 访问新映射的物理页
    L2->>CIU: 触发 Snoop 请求
    CIU->>C0: Snoop 请求（该行是否在核0 L1？）
    C0->>C0: 状态 M → O 或 I
    C0->>CIU: 返回数据（Cache-to-Cache）
    CIU->>C1: 数据传递
    C1->>C1: L1 获得数据<br/>状态 S 或 E

工程含义：TLB 一致性和 Cache 一致性走的是同一条 CIU 通道，但处理的是不同类型的事务（TLB 失效广播 vs. Cache Line 数据共享）。验证时需要确保两者在 CIU 中互不阻塞，且广播顺序正确。

六、C920 向量扩展对内存子系统的影响

C920 与 C910 最核心的差异是从 RVV 0.7.1 升级到 RVV 1.0，并可选配 128/256 位向量单元。这对内存子系统意味着：

对 TLB 的压力：向量单元一条指令可能访问跨多个页的大量数据。如果向量访存跨越页边界，DTLB 需要在同一周期内处理多个不同页的翻译请求。C910/C920 的 D-uTLB 双读端口设计在这里派上用场，但跨页向量访存场景下 TLB 缺失队列的分配策略需要特别关注。

对 Cache 带宽的要求：256 位向量一次 load 就是 32 字节，接近 Cache 行的一半。L1 D-Cache 的 8-bank 结构、每次最多 128bit 的读能力，在向量密集场景下可能成为瓶颈。C920 支持高性能数据预取，正是为了缓解这种压力。

七、各组件一句话总结

组件 一句话理解
DTLB/ITLB 全相联小缓存，DTLB 双端口支持双发射，不存 ASID 所以上下文切换要全刷
JTLB 4路组相联 256 项，存 ASID 所以进程切换不用刷，缺失时触发 PTW
PTW 最多 4 次访存遍历三级页表，借用 LSU 的 DC 流水线，期间阻塞 LSU 访存
L1 I-Cache VIPT 结构降低取指延迟，但容量超过 4KB×路数时有别名风险
L1 D-Cache PIPT 结构消除别名，8 Bank 支持双发射并发，自适应写分配优化连续写
L2 Cache 16路组相联共享，MOESI 协议支持 Cache-to-Cache 传输
CIU Cache Snoop 和 TLB Shootdown 的统一广播枢纽，保证多核一致性事件顺序
