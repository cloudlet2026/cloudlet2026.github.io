C910/C920：RISC-V 规范约束下的微架构实现

发表于2026-10-16|更新于2026-10-17
|浏览量:

结论前置

C910 与 C920 与伯克利前四代 RISC 原型没有继承关系。 C910 是玄铁基于 RISC-V 规范实现的商业处理器，其微架构（12 级乱序、3 发射、双 128 位向量）的技术源头是 1990s–2000s 商用乱序处理器传统（Intel P6、MIPS R10000、Alpha 21264），而非 SPUR 的“哑流水线级”或“寄存器窗口”。

C910 对 RISC-V 的更改分为三类：RVV 版本选择（0.7.1 而非 1.0，因流片窗口早于标准定稿）、约 100 条 vendor 自定义指令（使用 RISC-V 预留的 custom 编码空间）、DSA 扩展接口（异构耦合方案的一次工程验证，为后续标准化接口提供了实践参考）。这些更改不是对 RISC-V 规范的修改，而是在规范预留空间中的填充。C920v2 的核心更改是从 RVV 0.7.1 转向 RVV 1.0，这是“标准成熟后对齐”的选择。

但“更改”只是 C910/C920 的一小部分。 C910/C920 的微架构由三层构成：契约层（RISC-V 规范强制规定的行为）、实现层（RISC-V 规范未规定、由 T-Head 自主决策的微架构）、Vendor 扩展层（RISC-V 允许范围内的厂商自定义指令）。契约层必须遵守规范，实现层由 T-Head 自主决策，Vendor 扩展层在规范预留空间内由 T-Head 定义。

一、C910：首款规模化量产的高性能乱序 RISC-V 处理器

C910 是玄铁系列中首款实现规模化量产的高性能乱序 RISC-V 处理器，采用 12 级多发乱序流水线，典型工作频率大于 2.5GHz，采用 3 发射、8 执行的深度乱序执行架构。

1.1 核内单元构成

C910 核内子系统的明确命名单元：

单元 全称 功能
IFU Instruction Fetch Unit 指令提取
IDU Instruction Decode Unit 指令译码
IU Integer Unit 整型执行
FPU Floating Point Unit 浮点执行
LSU Load/Store Unit 存储载入
RTU Retire Unit 指令退休
MMU Memory Management Unit 虚拟内存管理
PMP Physical Memory Protection 物理内存保护

C910 的多核子系统包含：数据一致性接口单元（CIU）、二级高速缓存、主设备接口单元、可配置的 AXI4.0 设备一致性接口（DCP）、平台级中断控制器（PLIC）、计时器和自定义多核单端口调试框架。

C910 支持 RV64GCV 指令集，其中 G 代表通用扩展（包含基础整型 I、乘除法 M、原子操作 A、单精度浮点 F、双精度浮点 D、控制状态寄存器 Zicsr、指令流栅栏 Zifencei），外加压缩指令 C 和向量扩展 V。根据 cpuinfo 工具的输出，C910 实际报告的支持特性为 rv64imafdcsu，包括特权态（S）和用户态（U）支持。

1.2 微架构规格

C910 的性能数据：平均 IPC 为 1.61，CoreMark/MHz 为 4.86，得益于其先进乱序执行和 3 发射流水线。C910 配备 2 个 ALU、2 个 FPU 和宽 Load/Store 单元（2 loads 和 2 stores），在计算密集型和内存密集型任务中表现尤为有效。其分支预测结构包括 32K BHT 和 4K BTB，在分支密集的工作负载中显著提升性能。

1.3 分支预测：混合多模式

C910 采用混合分支处理技术，包括分支方向预测、分支地址预测、函数返回地址预测和间接跳转地址预测。这四种预测机制协同工作，覆盖了程序控制流的不同分支类型。对于 12 级深度流水线而言，分支预测精度直接决定流水线效率——一次预测失败意味着最多 12 个周期被浪费。

C910 还支持多通道多模式数据预取技术，显著提升数据访问带宽。预取器支持虚拟地址和物理地址预取，可配置预取容量。

1.4 多核一致性与缓存架构

C910 支持多核多簇 SMP，每个簇包含 1–4 个核心，簇间通过缓存一致性协议维护数据一致性。四核共享 L2 Cache，支持缓存数据一致性。这对于运行 Linux 操作系统的场景是必需的——多核 Linux 内核需要硬件级别的缓存一致性来保证多线程程序的正确性。

C910 的 L1 数据缓存支持快速内存加载，提前加载内存访问数据，减少 load-to-use 延迟。存储子系统还支持存储推测访问预测，预测随机内存乱序推测访问，提升执行效率。

1.5 MMU 与虚拟内存管理

C910 的 MMU 支持 Sv39 页表模式，虚拟地址位宽为 39 位。L2 联合 TLB 为 4 路组相联，1024 个表项。这一配置使 C910 能够运行 Linux 等现代操作系统，满足操作系统对虚拟内存管理的基本需求。

1.6 向量引擎：RVV 0.7.1

C910 的向量执行单元实现了当时相对成熟的 RVV 0.7.1 草案版本的 RISC-V 向量扩展规范。向量寄存器为 32 个 128 位 VGPR，AI 向量计算引擎采用双 128 位运算宽度，支持半精度/单精度/双精度/8 位/16 位/32 位/64 位并行计算。

C910 向量单元的性能：每 Cluster 超过 300 GFLOPS FP16。在矩阵乘法基准测试中，C910 上优化的 8×8 微内核相比 OpenBLAS 中的优化版本，对于足够大的矩阵可实现近 3 倍加速（15 GFLOPS vs. 5 GFLOPS）。

RVV 0.7.1 的选择背景：C910 的流片时间（2019–2020）早于 RVV 1.0 在 2021 年的正式批准。RVV 0.7.1 是当时唯一可用的向量规范草案。这直接导致了 C910 的向量二进制与标准 RVV 1.0 硬件不兼容。

二、C910 对 RISC-V 的更改：三类填充

2.1 RVV 版本选择：0.7.1 而非 1.0

更改内容：C910 实现的是 RVV 0.7.1 稳定草案，而非 2021 年批准的 RVV 1.0 。

原因：C910 的流片时间（2019–2020）早于 RVV 1.0 定稿。RVV 0.7.1 是当时唯一可用的向量规范草案 。T-Head 没有选择——等待 1.0 意味着推迟产品上市，这与商业竞争窗口不兼容。

0.7.1 与 1.0 的不兼容性：RVV 0.7.1 与 1.0 指令编码不兼容——不是“略微不同”，是二进制完全不兼容 。0.7.1 没有分数 LMUL（1/8、1/4、1/2），没有 vsetivli 立即数版本；C910 硬件实现中 Tail/Mask 策略是固定的（tail 置零），不支持 agnostic 模式；也没有用于上下文切换的整向量寄存器加载/存储指令。这意味着 C910 编译的向量二进制无法在标准 RVV 1.0 硬件上运行，反之亦然。

后果：C910 及其衍生芯片运行的是 xtheadvector（T-Head 命名的 vendor 扩展），Linux 内核需要 xtheadvector 补丁来区分“向量支持”的真实含义。社区有 RISC-V Vector rollback 脚本，可将 RVV 1.0 汇编转换为 0.7.1，但这是权宜之计而非标准方案 。

2.2 约 100 条 vendor 自定义指令

更改内容：C910 在 RISC-V 标准指令集之外实现了约 100 条扩展指令，使用 RISC-V 预留的 custom-0/custom-1 编码空间 。

原因：RISC-V 规范预留了 custom 编码空间供厂商自定义，但没有规定这些指令应该长什么样。T-Head 选择填充这些空间来加速特定工作负载，同时保持与 RISC-V 标准指令的共存。

指令分类 ：

子集 代表指令 目的
位操作 EXT/EXTU/FF0/FF1/REV/REVW/TST 位提取与反转
算术运算 MULA/MULAH/MULAW/ADDSL/MULS/SRRI 定点乘加/乘减
同步 SYNC/SYNC.I/SYNC.IS/SYNC.S 多核同步增强
Cache DCACHE.CIALL/ICACHE.IALL/L2CACHE.CALL 缓存管理
存储 LRB/LRH/LRW/LURB/LURH/LURW/LBIA Load+移位融合

在编译器中的状态：这些扩展已被 GCC、LLVM、Binutils、QEMU 上游接受，以 XThead* 系列命名 ：

  • XTheadBa：移位加法（th.addsl，1:1 映射到 Zba 的 shNadd）
  • XTheadMemIdx/XTheadFMemIdx：索引寻址模式
  • XTheadMemPair：双寄存器 load/store
  • XTheadMac：乘累加
  • XTheadSync：同步指令
  • XTheadCmo：缓存管理操作

XThead* 的实际效果：SPEC CPU 2017 评估显示，XTheadMemPair 在 C910/C920 上没有性能收益（对比两条独立内存访问），代码大小减少仅 0.1%（与 RVC 大量重叠）。XTheadBa 的评估则显示有改善，但幅度有限 。

2.3 DSA 扩展接口

更改内容：2024 年玄铁正式推出 DSA 扩展接口，允许用户挂载自定义加速器而不修改核心流水线 。

原因：C910 的 vendor 扩展指令与流水线的耦合方式使得调整扩展接口以适应新加速器需要大幅修改核心逻辑。DSA 接口的目的是把“扩展”从“改核心”变成“挂接口”。

接口机制：DSA 核心可以直接访问 C910 的寄存器资源和指令流（命令接口），通过流水线化的 L1 Cache 访问通道与内存交互（内存一致性由 C910 的 LSU 保证），并通过 L2 Cache 访问接口获得大带宽数据通道 。

意义：这不是“对 RISC-V 规范的改进”，而是对 RISC-V 扩展机制的一次工程验证——证明了 RISC-V 核心可以在不改流水线的前提下耦合领域专用加速器。

三、C910/C920 微架构的三层结构

“更改”只是 C910/C920 的一小部分。 C910/C920 的微架构由三层构成，三者不是“照搬”和“自研”的对立，而是“规范强制、实现自由、扩展允许”的并列关系。

3.1 契约层：RISC-V 规范强制规定的行为

这一层是 ISA 契约。RISC-V 规范规定了“处理器执行某条指令后，架构状态必须变成什么样”。任何 RISC-V 实现都必须遵守这些规定，否则就不是 RISC-V。

契约层的内容包括：

  • 32 个通用寄存器（x0–x31）：基础 ISA 强制。
  • 指令编码格式：RV64I 的 R 型、I 型、S 型等，是规范定义的。
  • CSR 编号和语义：mstatus、satp、mepc 等 CSR 的地址和字段含义。
  • Sv39/Sv48 页表格式：PTE 的位布局（V/R/W/X/U/G/A/D）。
  • CLINT/PLIC 的寄存器布局：非 ISA 规范，但 C910/C920 遵循了这些标准接口。
  • PMP 的 NAPOT/TOR 编码：权限位和地址匹配方式。

C910/C920 在这一层“遵守规范”，是因为这是成为 RISC-V 处理器的前提。不遵守契约层，程序就无法在 C910 上正确运行。

3.2 实现层：RISC-V 规范未规定、由实现者自主决策的部分

这一层是 微架构实现。RISC-V 规范只关心“结果对不对”，不关心“怎么得到这个结果”。C910/C920 在这一层做了大量自主决策：

  • 12 级流水线：RISC-V 不规定流水线深度。C910/C920 选择 12 级，是为了在 TSMC 12nm 工艺下达到 2.5GHz+ 频率。CVA6 同样实现 RISC-V，只有 6 级。
  • 3 发射、8 执行：RISC-V 不规定发射宽度。
  • 重排序缓冲（ROB）容量：C910 的 ROB 有 64 条目。RISC-V 没有任何规定。
  • 分支预测器结构：C910 的 BHT 有 32K 条目、BTB 有 4K 条目。这些数字是 T-Head 根据目标工作负载选择的。
  • 物理寄存器堆：配置数十个物理整型寄存器用于寄存器重命名（架构可见只有 32 个）。RISC-V 不规定重命名，更不规定物理寄存器数量。
  • LSU 的双发射乱序设计：RISC-V 的 A 扩展只定义 LR/SC 和 AMO 的语义，不规定 LSU 微架构。
  • 多核一致性协议：C910/C920 使用基于目录的 MOESI 协议和 Snoop Filter。RVWMO 只定义可见性规则，不规定用总线监听还是目录协议。
  • 缓存预取器：RISC-V 规范没有预取器这个概念。
  • L1 Cache 容量和组相联度：32KB/64KB、组相联度，都是 T-Head 的选择。

C910/C920 在这一层的决策，不来自 RISC-V 规范，而来自 T-Head 对目标工艺、目标频率、目标工作负载的工程判断。

3.3 Vendor 扩展层：RISC-V 允许范围内的厂商自定义

C910/C920 的 XThead* 扩展（XTheadBa、XTheadMemIdx、XTheadSync 等）是 T-Head 在 RISC-V 预留的 custom-0/custom-1 编码空间中填充的自定义指令。这些指令的存在是 RISC-V 允许的（规范预留了空间），但指令的编码和语义是 T-Head 定义的。它们既不是 ISA 契约的强制部分，也不是纯粹的微架构细节——它们是 ISA 层面的 vendor 扩展。

3.4 三层结构的总结

层面 内容 决定者 C910/C920 的状态
契约层 寄存器、指令编码、CSR、页表格式、PMP 编码 RISC-V 规范 必须遵守，否则不是 RISC-V
实现层 流水线深度、ROB 容量、分支预测器、LSU 微架构、多核协议 T-Head 自主决策 规范不规定，T-Head 根据工程约束选择
Vendor 扩展层 XThead* 系列 T-Head 定义，RISC-V 允许 填充 custom 编码空间，非标准

契约层是“必须遵守的规范”，实现层是“规范不干预的自主决策”，Vendor 扩展层是“规范允许范围内的厂商自定义”。 这三层的关系不是“照搬 vs 自研”，而是“ISA 契约、微架构实现、厂商扩展”的并列关系。

四、C920：从草案向量转向标准向量

C920 存在两个版本，向量支持不同。C920v2 转向标准 RVV 1.0，这是玄铁系列向量扩展的代际切换点。

4.1 版本差异

维度 C910 C920v1 C920v2
向量扩展 RVV 0.7.1 RVV 0.7.1 RVV 1.0
RVA Profile 无 RVA22 RVA22 + RVA23
Vector Crypto 无 无 有
MMU Sv39 Sv39/Sv48 Sv39/Sv48
FPU FP32/FP64（不支持半精度） BF16/FP16/FP32 BF16/FP16/FP32
最高频率 2.5GHz 2.5GHz 3GHz
最大核心数 16（4 核/簇 × 4 簇） 64 64

4.2 RVA23 Profile：C920 的规范对齐

C920v2 兼容 RVA23 规范。RVA23 是 RISC-V 应用级 Profile 的当前标准，定义了“一个现代应用处理器必须包含哪些扩展”。

RVA23 的强制扩展包括：

  • V 向量扩展：在 RVA22 中是可选的，RVA23 中成为强制
  • Zicond：条件零指令（无分支）
  • Zihintntl：非临时局部性提示
  • Zfa：附加浮点指令
  • Zawrs：低功耗等待
  • Zvfhmin：向量最小半精度浮点
  • Zvbb：向量基础位操作
  • Zvkt：向量数据无关执行延迟

RVA23 的一个关键设计决策是标量加密不再作为推荐配置：Zkn 和 Zks 标量加密扩展在 RVA22 中是可选组件，在 RVA23 中不再纳入推荐配置，目标是让硬件和软件厂商都转向向量加密，因为向量现在已是强制扩展，且向量加密比标量加密快得多。

4.3 RVV 1.0 的意义

SG2044 使用的 C920v2 是较早量产的、商业可用的、完全支持 RVV 1.0 的服务器级 RISC-V 处理器之一。C920v2 的 RVV 1.0 支持使玄铁向量生态从“0.7.1 孤岛”向标准靠拢，Linux 发行版、编译器、运行时可以基于标准 RVV 1.0 假设来优化 C920v2 的向量代码。

4.4 保留的 vendor 遗产

C920 保留了 C910 时代定义的 XThead* 系列扩展（XTheadBa/Bb/Bs/Cmo/CondMov/FMemIdx/Int/Mac/MemIdx/MemPair/Sync）。这些扩展已被 GCC 和 LLVM 上游接受，作为 -mcpu=thead-c920v1/v2 的一部分。C920 没有完全抛弃 T-Head 的扩展体系，而是在标准之外继续维护自己的扩展集合。

五、C910/C920 对 RISC-V 生态的影响

5.1 正面影响

验证了 RISC-V 可以做到商用级乱序性能。 C910 是首款规模化量产的 12 级乱序 RISC-V 处理器，证明了开放 ISA 可以实现与 ARM Cortex-A 系列同级别的微架构复杂度。

验证了 RVV 草案可以被商业硬件正确实现。 没有 C910 的大规模量产，RVV 工作组无法获得真实的性能数据和软件反馈。C910 的 RVV 0.7.1 实现为 RVV 1.0 的修订提供了“什么是可行的、什么是不方便的”的实践依据。

提供了 DSA 耦合的参考实现。 Xuantie DSA Interface 展示了 RISC-V 扩展机制在异构计算中的可行路径，为后续 CV-X-IF 等标准化接口的讨论提供了工程经验。

5.2 负面影响

RVV 0.7.1 的生态分裂。 C910 及其衍生芯片（Allwinner D1、SG2042 等）运行的是 xtheadvector，与标准 RVV 1.0 二进制不兼容。Linux 内核需要 xtheadvector 补丁来区分“向量支持”的真实含义——DT 中声明 v 不代表支持 RVV 1.0，可能只是 0.7.1。

自定义指令与流水线的紧耦合。 C910 的扩展指令与流水线的耦合方式使得调整扩展接口以适应新加速器需要大幅修改核心逻辑。这直接推动了标准化协处理器接口的讨论。

缓存管理 errata 增加了上游软件负担。 C910 的缓存操作方案与标准 Zicbom 存在行为细节差异，Linux 内核需要维护专门的适配代码来处理这一偏离。

六、总结：C910/C920 在 RISC-V 规范谱系中的位置

C910 是“在规范留白处填空”。 RISC-V 规范预留了 custom-0/custom-1 编码空间供厂商使用，C910 填充了其中的约 100 个槽位。RISC-V 规范允许 vendor CSR 区间，C910 在 0x5C0–0x7C7 和 0x702–0x705 中定义了 T-Head 特有的 CSR。RVV 0.7.1 是 C910 流片时唯一可用的草案，T-Head 没有等待 1.0。

C920v2 是“在标准成熟后对齐”。 RVV 1.0 切换是 C920v2 最核心的变更——C910 的 0.7.1 是流片窗口的产物，C920v2 的 1.0 是标准定稿后的选择。RVA23 兼容意味着 C920 不再是一个“T-Head 私有 ISA 的处理器”，而是一个符合社区共识的、可预测的 RISC-V 实现。

C910/C920 与前四代 RISC 原型之间没有继承关系。 它们的微架构单元来自 RISC-V 规范（契约层）+ 现代商用乱序处理器传统（实现层）。前四代 RISC 原型证明的“精简可行”、SPUR 引入的 MMU、RISC-II 确立的 32 个寄存器，是 RISC-V 规范继承的最基础遗产。C910/C920 是在这个遗产之上，用商业工程约束填充规范留白的具体实现。

C910/C920 对 RISC-V 的“更改”没有一项是修改 RISC-V 规范。 它们是在 RISC-V 预留的扩展空间中填充 T-Head 的实现，或在标准成熟后从草案转向标准。RVV 0.7.1 的选择是流片窗口的产物，XThead* 是 vendor 扩展，DSA 接口是异构耦合的工程方案。C920v2 的 RVV 1.0 和 RVA23 对齐则是“标准成熟后转向标准”的结果。
