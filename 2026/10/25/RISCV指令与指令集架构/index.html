第一层：为什么需要指令集架构（ISA）

问题：软件和硬件直接对话不可行

软件是一串高级语言逻辑，硬件是一堆晶体管开关。两者无法直接沟通——需要一个标准化接口让软件"告诉"硬件做什么。

解决：指令 → 指令集 → 指令集架构

概念 定义 说明
指令​ 指挥硬件完成某一基本操作的单条命令，由操作码+地址码组成 机器语言的基本语句，二进制编码
指令集​ 一台 CPU 能执行的全部指令的集合 二进制编码与操作的映射表
**指令集架（ISA）**​ 指令集的超集，软件与硬件之间的完整抽象接口规范 包含指令集 + 寄存器/内存资源 + 异常/中断模型

因果：CPU 硬件需要标准化接口 → 诞生 ISA → 软件编译后面向 ISA 编程 → 硬件实现 ISA 即可运行软件。

第二层：RISC-V ISA 的设计

问题：传统 ISA 绑定特定厂商

x86 封闭、ARM 授权昂贵 → 需要开放、模块化、可扩展的 ISA。

解决：基础 + 扩展模式

类别 名称 说明
基础指令​ RV32I 整数指令，32 个 32 位寄存器，寻址 32 位地址空间
RV64I 整数指令，32 个 64 位寄存器，寻址 64 位地址空间
RV128I 整数指令，32 个 128 位寄存器，寻址 128 位地址空间
RV32E 同 RV32I 但只暴露前 16 个寄存器（0~15），嵌入式省面积
扩展指令​ M 乘法、除法、取模求余
A 原子操作（比较并交换、读改写等）
F / D / Q 单精度/双精度/四倍精度浮点
C 压缩指令，单指令 16 位，改善程序大小
V 向量（SIMD）
P 单指令多数据（Packed-SIMD）
B 位操作
H 虚拟化（Hypervisor）管理指令
J 动态翻译语言
L 十进制浮点
N 用户中断
G 通用组合 = I+M+A+F+D
典型配置​ **RV64GC[V]**​ C910 采用的指令集（加可选向量扩展）

第四层：六种指令格式

问题：一条指令只有 32 位，但操作数需求不同

有的需要 3 个寄存器，有的需要 2 个寄存器+大立即数，有的需要 2 个寄存器+偏移量拆散存放。32 位装不下所有信息 → 按操作数模式分成六种格式。

第五层：寄存器文件与 ABI 命名

32 个通用寄存器

x0（0 值寄存器），x1~x31（常规寄存器）

x0 寄存器用途详解

1. 丢弃结果

  • add x0, x6, x7 → 计算结果写入 x0 = 丢弃
  • addi x0, x0, 0 → 空操作

2. 提供"绝对 0"常量

  • 清零寄存器：add x5, x0, x0（将 x5 变为 0）
  • 寄存器拷贝（伪指令 mv）：addi x5, x6, 0 等价于 add x5, x6, x0
  • 加载小常数（伪指令 li）：addi x5, x0, 5 即可把 5 放入 x5

3. 实现"无条件跳转"

  • 伪指令 j label：展开为 jal x0, label。跳转到 label，把返回地址存入 x0（丢弃），实现无条件跳转
  • 伪指令 ret（函数返回）：展开为 jalr x0, 0(ra)。跳转到 ra 保存的地址，不保存新返回地址

4. 简化分支条件

  • 伪指令 beqz x5, label：展开为 beq x5, x0, label（如果 x5 等于 0 则跳转）
  • 伪指令 bgtz x5, label：展开为 blt x0, x5, label（如果 0 小于 x5，即 x5 大于 0，则跳转）

5. 在内存中写入 0

  • sw x0, 0(sp) → 把 0 存入栈顶指向的内存

第六层：从汇编到机器码

问题：人写二进制不可行

机器指令是二进制编码，直接写 0 和 1 极其困难。汇编语言用助记符（如 mov、add）和符号替代二进制码，但每条汇编指令都精确对应一条机器指令。"汇编"一词英文为 assembly（集合、装配），取"汇集符号、编码成机器码"之意。

例如 x86 下：mov eax, 1 → 机器码 B8 01 00 00 00。对应关系由 ISA 事先规定。

PC 与指令地址：为什么汇编器需要"两遍扫描"

要理解汇编器怎么工作，先要分清两个容易混淆的概念：

  • 指令地址：内存中某条指令的固定位置，客观存在，由链接器最终确定
  • PC：一个寄存器，动态地"指着"某条指令的地址，随执行不断变化

汇编器在第一遍扫描时，并不知道每条指令最终会被放在内存的哪个地址（因为还要等链接器分配），但它需要立即处理分支跳转和符号引用——这些指令的偏移量依赖目标地址。所以汇编器先用标签建立符号表，第二遍再回填地址。

汇编器的"翻译"机制：查表 + 编码

汇编器不需要"理解"程序逻辑，只做两件事：

1. 查指令编码表

ISA 为每条指令定义了固定的二进制格式（操作码字段 + 操作数字段）。汇编器内部维护 opcode 表：

  • GNU binutils（as）：源码 opcodes/ 目录有 i386-opc.tbl、arm-opc.h 等，构建时编译进二进制
  • LLVM：用 TableGen 从 .td 描述文件自动生成 C++ 编码代码
  • 商业编译器（Keil、IAR）：编码表直接内置

2. 处理符号地址（两遍扫描）

汇编器第一遍时并不知道每条指令最终会被放在内存的哪个地址——链接器还没运行，段地址未定。但它需要立即处理分支跳转和符号引用，这些指令的偏移量依赖目标地址。所以：

  • 第一遍：记录所有标签和符号，建立符号表，确定相对段起始的偏移量
  • 第二遍：生成机器码时查符号表填入正确地址或偏移量

这里要分清两个容易混淆的概念，它直接影响为什么必须两遍扫描：

  • 指令地址：内存中某条指令的固定位置，客观存在，但最终由链接器分配
  • PC：一个寄存器，动态地"指着"某条指令的地址，随执行不断变化

从源码到 CPU 取指：完整构建链路

汇编器产出目标文件（.o / .obj）后，指令并没有直接交给 CPU——中间还隔着链接和加载两步。

编译阶段：高级语言 → 汇编语言（编译器如 GCC/Clang）

汇编阶段：汇编语言 → 机器指令（汇编器如 as），产出目标文件

目标文件不能直接执行，有三个原因：

原因 说明
符号未解析 调用了外部函数（如 printf），汇编时不知道它在哪，.o 里只留了"待填坑"标记
地址未确定 每条指令的地址只是"相对段起始的偏移"，不是最终内存地址
代码不完整 main.o 调用了 libc 里的函数，但 libc 的代码还没合进来

链接阶段：链接器（ld）合并多个 .o 文件和库，做两件事——

  1. 符号解析：A 文件调用 foo，B 文件定义 foo，链接器把它们绑在一起
  2. 重定位：给每条指令分配最终内存地址，把"待填坑"偏移量回填为真实地址

产出 ELF 可执行文件，所有符号已解析、所有地址已确定，但还在磁盘上。

加载阶段：运行程序时，操作系统加载器为进程分配虚拟地址空间，把 ELF 的代码段（.text）、数据段（.data、.bss）映射到内存，设置 PC 指向入口点（_start → libc 初始化 → main）。

执行阶段：CPU 从入口地址开始逐条取指、译码、执行。

第七层：内存栅栏

问题根源：性能优化引入的硬件结构，各自打破了一种"应该看到"的保证

现代 CPU 为性能引入多种硬件结构，但它们不是同一个问题的三种表现，而是三个独立的问题，各自需要专门的栅栏指令解决：

硬件结构 打破的保证 对应栅栏
Store Buffer + 乱序执行 多核间访存顺序与程序顺序一致 FENCE
I-Cache 与 D-Cache 独立 数据写入对指令取指可见 FENCE.I
TLB 缓存页表项 页表修改对地址翻译可见 SFENCE.VMA

7.1 普通内存栅栏：FENCE

  • 问题根源：Store Buffer 延迟写全局可见 + Load 乱序执行。Core A 的写操作卡在 Store Buffer 中尚未刷入 L1 D-Cache，Core B 就已经发起读操作，读到旧值。或者 Core A 的两次写因 Store Buffer 刷新时机不同，Core B 观察到与程序顺序相反的写入次序。这是唯一由 Store Buffer 和乱序执行共同导致的问题。
  • 作用：确保在 FENCE 之前的访存操作，在全局看来一定先于它之后的访存操作完成。它强制 CPU 等待 Store Buffer 排空、所有 pending 的 load/store 完成后再执行后续访存。
  • 精细控制：操作数如 rw, rw 控制对读（R）/写（W）排序。Linux smp_mb() → FENCE rw, rw；smp_wmb() → FENCE w, w；smp_rmb() → FENCE r, r
  • 典型场景：多核并发与无锁队列。核心 A 写链表节点后把全局指针指向它，必须插入 FENCE 确保节点数据先写入内存（Store Buffer 排空），别的核心顺着指针读时才能看到完整数据。驱动程序写外设寄存器（MMIO）也必须用 FENCE 保证配置寄存器和启动寄存器的写入顺序。

7.2 指令流栅栏：FENCE.I

  • 问题根源：CPU 有专门的指令缓存（I-Cache），取指速度极快。当软件往内存写了新机器码，写操作走 D-Cache（或 Store Buffer → D-Cache），但取指令走 I-Cache。I-Cache 里缓存的还是旧指令。这与 Store Buffer 和乱序执行无关——即使写操作立刻全局可见，I-Cache 照样不知道内存被改了。单核 JIT 编译就会触发此问题。
  • 作用：保证在 FENCE.I 之前的数据写入，对后续取指单元可见。清空 I-Cache 中对应缓存行，强制 CPU 重新从内存取最新指令。
  • 与 SFENCE.VMA 的关系：两者职责严格分离。FENCE.I 管指令缓存一致性，SFENCE.VMA 管 TLB。某些处理器实现中 SFENCE.VMA 可能间接触发 I-Cache 失效，但这不是 RISC-V 规范保证的行为，不能依赖。
  • 典型场景：JIT 编译器（Java VM、JS 引擎）和动态链接器。程序运行时把源码动态编译成机器码写进内存后，必须执行 FENCE.I 把 I-Cache 旧代码洗掉，强制 CPU 重新从内存取最新指令。如果没有 FENCE.I，CPU 可能会去 I-Cache 里拿旧指令执行，或者拿到写了一半的残缺指令。

7.3 地址翻译栅栏：SFENCE.VMA rs1, rs2

  • 问题根源：操作系统在内存里修改了页表（比如把某个页的权限从"只读"改成"可写"），或者分配了新的物理内存。但是 CPU 的 TLB（地址翻译缓存）里还留着旧的映射。如果不刷 TLB，CPU 依然按旧规则访问。这与 Store Buffer 和乱序执行无关——即使页表修改立刻全局可见，TLB 也不会自动失效。单核切换进程就会触发此问题。
  • 作用：强制刷新 TLB，让硬件重新查询内存中的页表，看到软件对 PTE 的最新修改。
  • 扩展：虚拟化支持（Hypervisor 扩展）下还有 HFENCE.VVMA（Guest 虚拟地址）和 HFENCE.GVMA（Guest 物理地址）。
rs1：虚拟地址 rs2：ASID 操作
0 0 无效 TLB 中所有表项
非零 0 无效 TLB 中所有命中 rs1 虚拟地址的表项
0 非零 无效 TLB 中所有命中 rs2 进程号的表项
非零 非零 无效 TLB 中所有命中 rs1 虚拟地址和 rs2 进程号的表项
  • 典型场景：操作系统处理缺页异常（Page Fault），填补页表后必须执行 SFENCE.VMA 踢掉旧 TLB 表项。进程切换、修改代码段权限时也必须用它同步地址翻译状态，同时负责通知其他 CPU 核心一起刷新（TLB Shootdown）。

7.4 虚拟化陷阱：mstatus.TVM

SFENCE.VMA 受 mstatus.TVM（Trap Virtual Memory）监管：

TVM 值 行为
0（默认） S-mode 直接执行 SFENCE.VMA，硬件直接刷 TLB
1​ S-mode 执行 → 触发非法指令异常 → 陷入 M-mode → M-mode 检查合法性 → 用特权指令强制刷新物理 TLB → 修改 PC 跳过该指令 → mret 返回 S-mode

用途：Type-1 虚拟化、高安全隔离区（TEE）等场景。TVM=1 时 M-mode 替 S-mode 刷 TLB 比 S-mode 自己刷慢得多——这就是虚拟化的代价。
