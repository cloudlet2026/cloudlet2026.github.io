缓存与内存模型

发表于2026-10-25|更新于2026-10-25
|浏览量:

第一层：CPU 与主存之间的速度鸿沟

问题：CPU 等内存等得越来越久

CPU 速度的提升超过了内存访问速度的改进。"等内存"从偶尔发生变成常态——主存慢（介质慢、距离远、协议开销），物理和成本上存在「快的做不大，大的不够快」的硬约束。

解决：缓存（Cache）

基本思路：用一小块高速存储器，保存 CPU 最近用过、以及附近会用到的数据，放在离核心最近的地方。

能实现的理论基础——程序的两个局限性（对典型程序行为的统计观察）：

  • 时间局部性：刚用过的数据，很可能马上再用。→ 循环反复访问同一批变量和指令，让热点留在缓存里。
  • 空间局部性：用了某个地址，很可能接着用相邻地址。→ 数组、结构体、顺序执行的代码在内存中连续，让"取一块、用一片"划算。

新问题：单级缓存无法兼顾速度和容量

容量大 → 面积大 → 延迟高；容量小 → 命中率低 → 没有效果。

解决：多级缓存（L1/L2/L3 分层）

每一级都是「容量、速度、成本」的不同折中点：

  • L1：最小最快，兜住最热的数据
  • L2：较大稍慢，接住 L1 未命中
  • L3：更大、多核共享，作为去主存前的最后缓冲

用分层模拟"又大又快"。

第二层：多级缓存带来的组织方式问题

问题：多级缓存下，同一数据在 L1 和 L2 各有一份，如何管理？

需要决定"L2 是否必须包含 L1 的所有内容"，这直接影响一致性检查和容量利用。

解决：包含式 vs 非包含式

方案 做法 优点 代价
包含式​ L2 包含 L1 全部内容 一致性检查简单（查 L2 就知道 L1 有没有） 容量重复浪费
非包含式​ L2 不强制包含 L1 容量利用更充分 一致性维护复杂，需额外追踪机制

典型实施例：

  • 指令缓存与 L2 之间采用包含式：指令缓存只读，不会产生脏数据。L2 淘汰某条指令时直接使 L1I 副本失效，管理简单且无写回开销。
  • 数据缓存与 L2 之间采用排他式（非包含的一种）：数据可写，会产生脏行。L1D 淘汰干净行直接丢弃、脏行才写回 L2，减少不必要的数据搬运，提高有效容量。

新问题：写操作每次都同步到主存太慢

如果每次写都跑主存，写延迟高、带宽浪费大。

解决：写策略——写回 vs 写直达

方案 做法 优点 代价
写直达​ 每次写同步到主存 缓存和主存永远一致，无脏行 每次写都付主存延迟，占用带宽
写回​ 先改缓存，标记脏行，换出时才写回 同一行多次修改只写回一次，写快、带宽省 引入脏行，主存暂时过时

写回的直接目的：

  1. 减少写主存次数
  2. 降低写延迟（缓存内完成）
  3. 节省主存带宽

多级缓存通常在高层（L1/L2）用写回策略。

新问题：缓存和主存之间传输的最小单位怎么定？

解决：缓存行（Cache Line）

基于空间局部性，一块一块搬运，后续对相邻地址的访问直接命中缓存。缓存行既是主存和缓存之间传输的最小单位，也是缓存里占一格的单位，还带着标签、有效位、脏位等元数据。

  • 脏行（Dirty Line）：CPU 改过但还没写回主存的缓存行
  • 干净行（Clean Line）：和主存数据一致的缓存行

第三层：多级缓存的物理布局

问题：多级缓存在物理上怎么放？

逻辑上分了 L1/L2/L3，但物理位置直接决定访问延迟和带宽。

解决：L1 紧耦合在核内，L2 松耦合在核外

L1 必须在核内的原因：

约束 说明
延迟预算只有 3~4 个周期​ IF 和 MEM 阶段每周期都要访问 L1。电信号在硅片上传导距离稍远就吃掉好几个周期
带宽需求极端​ 4 发射核心每周期可能同时需要：取 4 条指令（L1I）+ 读 2 个源操作数（L1D）+ 写回 1 个结果（L1D）→ 3~5 次访问/周期，需要多端口 SRAM + 超宽数据通路（64~128 字节），只有专用接口能满足
私有性​ L1 里是当前线程的指令和栈数据，别的核几乎不碰。私有缓存每拍都不需要跟别的核"打招呼"，零仲裁延迟

L2 在核外（松耦合）的原因：

约束 说明
延迟容忍度高​ L1 命中率通常 90~95%，L2 访问只占 5~10%。偶尔多花 10~20 周期对整体 IPC 影响有限
共享需求​ 多核交换数据（共享变量、锁、消息队列）时，共享 L2 能直接转发（cache-to-cache transfer），不用下探到主存
容量和面积​ L2 容量是 L1 的 4~16 倍，大块 SRAM 挤进核心会挤压 ALU/寄存器堆面积，且漏电和动态功耗拉高核心电源轨
一致性汇聚点​ 所有核的 L1 缺失请求都经过 L2，天然适合做目录/嗅探过滤器，跟踪"谁持有了哪行、什么状态"

新问题：L2 在核外的具体放置方式因架构而异

设计 L2 位置 理由
Intel Core​ 核内私有（256KB~2MB） 每个核有自己的大 L2，L3 才是共享层
Apple M 系列​ 核内私有（12MB+） 超大 L2 靠高命中率减少对共享层的依赖
ARM big.LITTLE​ cluster 内共享 4 大核或 4 小核共享一个 L2，cluster 间走 L3
C920 多核簇​ cluster 内共享 4 核共享一个 L2，平衡延迟和核间通信

核心结论：L1 在核内 = 延迟预算极紧 + 带宽极端 + 私有性；L2 在核外 = 延迟容忍 + 共享需求 + 容量/面积 + 一致性汇聚。不是物理定律，是四个力拉出来的最优解。

新问题：L1 分离 + L2 在核外，但取指和访存仍可能争抢同一资源

第四层：缓存引发的流水线结构冒险

问题：经典五级流水线中 IF（取指）和 MEM（访存）争抢同一 L1 缓存端口

同一周期既要取指令又要读数据 → 结构冒险 → 流水线被迫停顿。

解决：改进哈佛结构（L1 分离指令和数据）

把 L1 拆成 L1I（指令缓存）​ 和 L1D（数据缓存），取指和访存各走各的通路，同周期并行。

新问题：如果彻底回到原始哈佛结构（双物理地址空间）

指令和数据放在完全独立的两个存储器里 → 软件加载麻烦、无法统一寻址。

解决：只在 L1 用哈佛，L2 及以下回归冯·诺依曼结构

  • 冯·诺依曼结构：指令和数据在同一存储器，同一地址空间、同一组总线访问
  • 改进哈佛：L1 分离解决端口冲突，L2 以下统一避免加载/寻址麻烦

这是通用计算机领域冯·诺依曼成为主流的原因——软件生态和统一寻址的便利性压倒了纯哈佛的理论优势。

第五层：多核带来的缓存一致性问题

问题：多核各有私有缓存，同一地址出现多副本

没有一致性协议时，Core B 永远读到旧值，程序逻辑悄悄崩溃。

解决：缓存一致性协议（MESI）

保证「同一个内存地址」在多个核心的私有缓存里不出现分裂。经典教材定义两条不变式：

不变式 含义
**SWMR（单写者-多读者）**​ 任意时刻，一条缓存行要么只有一个核可写，要么多个核只读，二者互斥
数据值不变式​ 对任意地址的读，必须返回该地址所有写操作全序里"最新那次"的值

每条缓存行维护四种稳定状态：

状态 含义 独占？ 和内存一致？ 本核能写？
M​ (Modified) 脏数据，唯一副本 ✅ ❌ ✅
E​ (Exclusive) 干净，唯一副本 ✅ ✅ ✅ 静默升级 M，零总线流量
S​ (Shared) 干净，可能多核共享 ❌ ✅ ❌ 写前需拿独占权
I​ (Invalid) 副本无效 — — ❌

新问题：MESI 中 M 态被其他核读取时，必须写回内存再让对方读

数据明明就在 A 的缓存里，却要绕一圈内存 → 浪费带宽。

解决：MOESI（加 Owned 态）

场景 MESI MOESI
M 态被别的核读 写回内存 → 双方变 S A 保持 O，直接给 B，B 进 S，不碰内存​
O 被驱逐 — 必须写回（它是脏数据责任人）

O 的本质：脏数据但允许别人持有只读副本，把"写回内存"和"共享"解耦。AMD/ARM 常用 MOESI；Intel 服务端常用 MESIF。

新问题：协议怎么让多核"互相看见"？

解决：两种实现路径

方案 做法 优点 代价
总线嗅探​ 所有缓存控制器监听共享总线上的一致性事务 实现简单，2~8 核高效 广播不随核数扩展
目录协议​ 目录记录每条缓存行被哪些核持有，点对点通知 扩展性好，适合多核/多 socket 目录本身有存储和维护开销

新问题：缓存一致性「管不到」的地方

  1. 伪共享：两个核写不同变量，碰巧在同一条缓存行 → 整行反复失效，性能断崖下跌（值永远正确）。解法：alignas(64) 或 padding 隔开。
  2. 不保证内存可见顺序：Store Buffer、乱序执行让别的核可能先看到后面的写。需要内存一致性模型。
  3. 普通 counter++ 不是原子操作：读-改-写三步之间可被别的核插进来。需要原子指令/锁。

第六层：内存一致性模型

问题：即使缓存完全一致，多核看到的读写顺序仍然不确定

根因：写的全局可见被 Store Buffer 延迟，而读不等人。

缓存一致性协议（MESI/MOESI）只管得住已经进入 L1 Cache 的缓存行状态。但 store 指令执行完毕后，数据先进 Store Buffer，还没进入 L1——此时别的核根本看不到这次写。而 load 指令直接从 L1 读数据，不等前面的 store 刷出去。

这就制造了一个时间差：写的对外广播被缓冲延迟了，读没有这个延迟，两者生效时间不对齐。

在顺序执行的处理器上，这是唯一一种由硬件制造的"重排"——写后读（Store-Load）从外部看像被颠倒了顺序。乱序执行只是进一步放大了这个窗口。

结果：Core 0 和 Core 1 都读到 0。

内存模型 是否允许这种结果 原因
SC（顺序一致性） ❌ 不可能 要求每个核的读写严格按程序顺序全局可见，store 必须对外生效后才执行下一条
TSO（x86） ✅ 允许 顺序执行但有 Store Buffer，唯一允许的 Store-Load 重排
RVWMO / ARM 弱模型​ ✅ 允许，且重排更多 乱序执行进一步放大，不止 Store-Load

一句话：Coherence 保证"同一份数据不打架"，但 Store Buffer 让写延迟全局可见、读提前执行——多核看到的读写顺序因此偏离程序顺序。这不是缓存的错，是 Store Buffer 这个"一致性协议盲区"制造的写后读时间差。

解决：内存一致性模型 = 约束 Store Buffer 何时必须排空

内存一致性模型本质上是硬件与软件之间关于 Store Buffer 行为的契约：

  • 硬件承诺：在哪些情况下，Store Buffer 里的写必须在后续操作之前排空（让其他核能看到）
  • 软件承诺：在需要严格顺序的地方，用 fence / 原子指令告诉硬件"这里不能偷懒"

不同模型的区别，就是允许 Store Buffer 延迟多久、延迟到什么程度：

模型 Store Buffer 约束 重排自由度 代表
SC​ 每条 store 必须排空到 L1 后，后续指令才能执行 零重排 理论模型
TSO​ store 进 Buffer 即可继续；只要求同核后续 load 能从 Buffer 转发到最新值，但其他核可以暂时看不到​ 仅允许 Store-Load 重排 x86
RVWMO​ 同 TSO 的 Store Buffer 行为；但给了更多实现自由度（如 store 可按不同路径到达其他核、更灵活的合并/刷出策略） 默认仅 Store→Load 不保序，实现可更激进 RISC-V

📌 TSO 和 RVWMO 的默认保序规则几乎相同——都只不保序 Store→Load（写后读）。区别在 RVWMO 给了更多微架构自由度，且 fence / 原子语义更细粒度。

RISC-V 的选择：RVWMO

RVWMO 的保留程序顺序规则——无 fence / 原子指令时：

前操作 后操作 是否保序 硬件实际行为
Load Load ✅ 按序或乱序均可，但全局可见顺序需保序
Load Store ✅ load 完成后 store 才全局可见
Store Store ✅ Store Buffer 按 FIFO 刷出
Store​ Load​ ❌ 不保序​ store 在 Buffer 里，load 就提前从 L1 读了

软件约束手段：强制 Store Buffer 排空或等待

1. fence 指令——显式冲刷

硬件执行 fence 时的实际动作：

  • 标记 fence 为同步点
  • 后续所有访存指令暂停发射，直到 Store Buffer 中 fence 之前的所有条目全部刷入 L1（且对其他核可见）
  • 这是"暴力"方案，会阻塞无关操作

2. 原子指令的 acquire / release 语义——精细约束

语义 硬件行为 对应直觉
release（rl 位） 前面的所有 store 必须排空到 L1（全局可见）后，才执行这条原子写 “释放锁：先把所有修改刷出去，再让别的核看到锁可用”
acquire（aq 位） 后面的所有 load/store 不能提前到这条原子读之前执行​ “获取锁：拿到锁之后才能读共享数据”

比全屏障 fence rw,rw 轻量——只约束特定方向的顺序，不阻塞无关操作。

新问题：乱序执行想尽可能重排，内存模型是红线

乱序执行器会尽量让 load 提前执行、store 延迟刷出，最大化并行度。内存模型就是不可逾越的红线：

  • 流水线中插入检查逻辑（LSQ 依赖检查、Store Buffer 转发规则、store-to-load forwarding 的地址匹配）
  • fence 到来时，硬件必须暂停后续访存指令的发射，轮询 Store Buffer 排空状态
  • 原子指令的 aq/rl 位触发类似的同步点，但只影响特定指令窗口，代价更小

第七层：缓存的其他配套优化

问题：缓存满了，新数据进来该换出哪行？

解决：替换策略（LRU 及近似）

优先淘汰最久没被访问的行，利用时间局部性。精确 LRU 硬件开销大，实际多用伪 LRU、时钟算法等近似方案。

新问题：即使有缓存，未命中时仍要等主存

解决：预取（Prefetch）

根据访问模式（如顺序访问数组）预测接下来要用的地址，在真正被请求之前就取进缓存。代价：预取错了会浪费带宽和容量，激进程度需权衡。

附：两条线对照

缓存一致性（Cache Coherence） 内存一致性（Memory Consistency）
解决什么​ 同一地址的多缓存副本是否一致 不同地址的读写，全局可见顺序是什么
关注点​ 数据正确性（多副本同步） 顺序可见性（多核观察顺序）
没有缓存时​ 不存在 依然存在
典型机制​ MESI/MOESI SC/TSO/RVWMO

RISCV五级流水线与三大冒险
第一层：为什么要引入流水线 问题：单周期 CPU 硬件大量闲置 在单周期 CPU 中，一条指令必须走完"取指、译码、执行、访存、写回"所有步骤才能执行下一条。大量硬件资源在绝大部分时间里处于闲置状态——比如执行阶段 ALU 在干活，寄存器堆、存储器接口、写回逻辑全在围观。 解决：流水线（时间重叠的魔术） 把一条指令的执行过程拆分成多个独立的步骤，每个步骤由专门的硬件负责。当第一条指令在"执行"时，第二条指令正在"译码"，第三条指令正在"取指"。通过时间上的重叠，让多个硬件单元并行工作。 理想目标：让每个时钟周期都能完成一条指令，CPI（每指令周期数）逼近 1，吞吐量提升 5 倍（对应 5 级流水线）。 新问题：一旦引入流水线，三大冒险立刻把管线卡得死死的 后一条指令如果必须等前一条的结果，流水线就得停。时间重叠的前提是指令之间互不依赖，而现实程序充满依赖。 第二层：经典五级流水线的骨架 解决：拆成五个阶段，用流水线寄存器隔离 每条指令依次经过五个阶段，阶段之间插入流水线寄存器保存中间结果和控制信号——...
